### E2E Flows
**Complete: 8. Broken: 0.**

1. **One stored switch.** The control panel (`control_panel.html:649`, `options.js:2401/9752`) and the settings tool both write `chrome.storage.local.fsbJevFastModeEnabled`. The probe confirms the settings write stores a real boolean: `planWrite('…','true')` gives `{fsbJevFastModeEnabled:true}`, and `'false'` gives `false`. Three places read it, all requiring `=== true`:
   - session start, `background.js:14215/14248`
   - follow-up commands, `:4170`
   - every fast turn's `readSwitch`, `:4104-4113` and `jev-fast-path.js:1480`

   A string `"true"` gives `null`. The source decides the budget profile: `'mcp'` gets `run_task`, every other source gets `autopilot`.
2. **Autopilot fast step (68 using 67).**
   - The agent loop asks the fast path for a step (`agent-loop.js:1941`).
   - The fast path fetches the page menu, builds the request with `FsbJevState.buildRequest` and calls `FsbJevClient.decide`.
   - `evaluateDecision` reads the answer only through `FsbJevPolicy.accept`, which returns `not_calibrated` for any status other than `'calibrated'` (`jev-policy.js:136`).
   - `buildStaticCall` builds the call, which goes through the permission hook and then the content script's strict resolver (`messaging.js:1043`).
   - Only `profiles/uncalibrated.json` ships. A session that never sees a calibrated answer latches off after one request (WR-04, `jev-fast-path.js:1591-1603`).
3. **run_task fast loop (70).** The bridge captures the fast-mode session at start (`mcp-bridge-client.js:2677-2682`). At settle it calls `buildFastModeBlock` and appends `fast_mode` as the last key (`:2783-2806`). The MCP response passes it through intact (`tests/mcp-run-task-fast-caller.test.mjs`). In the probe a real run_task-profile loop produced `{outcome:'done', reason:'complete_task', budget_profile:'run_task', jev:{attempts:2, fast_steps:1, calibration:'calibrated', …}}`.
4. **Measurements to bench to gate (66, 68, 70, 71).**
   - The session's `jevMeasurement` is saved by `automation-logger.js:1104/1112` and projected by `projectJevMeasurement` in `get_session_detail` (`mcp-tool-dispatcher.js:2363-2368`).
   - The bench copies it into the raw record (`run-bench.mjs:977`).
   - `toCommittedRow` then gives a v2 row with `jev.source:'measurement'`, `acted:true` and `calibrationStatuses {calibrated:1}`.
   - `validateCommittedRow` returns `{ok:true}`.
   - `exerciseStats` returns `exercised`.
   - A typed `done` on a run whose checker failed gives `claimedSuccessOnFail`.
   - The 'off' row has `jev.source:null` and `fastMode:null`, so there is no condition leak.
   - The fallback and calibration vocabularies are identical across the extension, the server and the bench.
5. **Bench applies the condition (66.1 + 71).** `writeSetting(...,'true'|'false')` goes through the settings tool. A CDP readback of the same key must then match (`run-bench.mjs:1331-1352`), and the preflight requires `type:'boolean'` from the read-one fields (`settings.ts:30`).
6. **`expect` and change_report redaction are unaffected by fast mode.**
   - `expect` is MCP-only by design (69 D-11). The 68 and 70 fast paths never call `evaluateExpectation` (70 CONTEXT:154) and produce no change_report.
   - The dispatcher's action, expect and redaction path reads no fast-mode state.
   - The content script's Jev branch fires only when `params.jevHandle` is present, and the MCP tool schemas drop unknown keys like that.
   - The redaction suites (`change-report-redaction`, `expect-dispatcher`, `mcp-expect-wire`, `expect-outcome-browser`) pass with the 68 and 70 code in the tree.
7. **Switch off behaves as before.** Every agent-loop change since 8a058bdf is guarded by `session.fastMode` or `_fastStep`. Golden-file tests pass for:
   - the loop (`tests/fixtures/jev-fast-loop-off-golden.json`)
   - run_task's wire output (`run-task-wire-golden.json`)
   - the saved logger session and the `get_session_detail` output (both off-mode goldens)
8. **Fast-path request to server validator (68 to 67).** Both requests the real loop sent pass `showcase/server/src/jev/validator.js` `validateRequest`. They carry `kinds` operation, target, completion and stuck, with no risk kind.

#### Warnings
- **W2:** JEV-06 relies only on the existing permission, consent and breaker gates. No Jev risk question is asked, and Jev cannot add a confirmation in this milestone (the hook above is deferred until after V3).
- **W3:** Turning fast mode on through the MCP settings tool skips the D-06 disclosure card. 70-VERIFICATION:161 lists the M-70-08 consent review as blocking release (V6).
- **W4:** run_task's added `fast_mode` key (only when the switch is on) goes beyond MCP-04's literal allowance (`expect` and the settings tool). The D-17 amendment is pending at V6. `tests/fixtures/mcp-release-delta-0.12.0.json` covers tools, parameters and message types, but not response keys.
- **W5:** With the switch off, a follow-up command now does one extra `chrome.storage.local` read (up to 3 s) before the loop restarts (`background.js:14102`). Outputs are unchanged, but I/O and timing are not strictly byte-for-byte.
- **W6:** When a run has no `jevMeasurement`, the bench falls back to the run_task summary's `calibration`, which is the last attempt's status, not the acted attempts'. This can only misreport toward `not_exercised` (the safe direction).
- **W7:** The gate measures only run_task (the Phase 70 profile). The 68 side-panel autopilot path is not measured separately (gate note D-05). The two `BUDGET_PROFILES` are numerically identical today (12/16/20000/3/3).
- **W8:** `FsbJevClient.ENDPOINT` is hard-coded to production (`jev-client.js:73`), so V3 and V4 'on' runs need the production gateway enabled with a calibrated profile (V2/V3 first).
