# Phase 53.1 Pattern Map

## Scope

This map is limited to the five gaps established by `53.1-VERIFICATION.md` and
`53.1-REVIEW.md`. It identifies proven repository patterns and failure modes; it
does not prescribe a new architecture.

No new production filename is compelled by the evidence. If planning extracts a
shared classic-script utility, use the module/export conventions cited below,
but do not infer that extraction from this map alone. The generated profile index
is an output: change its generator and regenerate it; never hand-edit it.

## Pattern 1: Validate Collectability Before Advertising Actionability

### Proven pattern

The repository already separates an actionable row from an inert status row.
`normalizeGroups` in the composer is the switch point, and the shell has matching
button/static renderers. The missing predicate is schema-aware collectability;
T1 readiness alone is not that predicate.

```js
// extension/content/skopeo-adaptive-composer.js:447,452-463
interactive: true

// Existing demotion shape
interactive: false
```

The canonical execution validator already exists below the UI. It uses the
resolved handler schema, rejects remote references, and invokes the same
cfworker JSON Schema implementation used by execution:

```js
// extension/utils/capability-router.js:94-128
_handlerParamsSchema(entry)
_validateHandlerParams(entry, params)
```

The runtime payload also already accepts arguments:

```js
// extension/content/skopeo-runtime.js:774-793
function actionPayload(action, tuple, slug, args, actionToken) { ... }
```

Therefore the established flow to preserve is:

```text
generated schema/actionability
  -> bounded projection
  -> composer actionable or static row
  -> shell collection/selection event
  -> runtime actionPayload(..., args, ...)
  -> background/router canonical validation
```

### File assignments

- The generator/projector own the data fact that reaches the composer.
- The composer owns actionable-vs-static view-model shape.
- The shell owns the UI event, but not schema authority.
- The runtime owns generation-scoped collection/pending state and argument
  transport. Its current `invokeSelectedRead` and `openSelectedConsequence`
  hardcode `const args = {}` at `827-880`.
- The background/router remain the final validators; client-side collection is
  not authorization.

### Regression pattern

Use three fixture classes in composer/runtime tests:

1. a capability valid with `{}` (including a schema with many optional fields),
2. a capability whose required primitive arguments are collectable,
3. a capability whose schema cannot be represented by the supported collector.

Assert that classes 1 and 2 can reach `actionPayload` with their actual args,
class 3 renders through the existing static row path, and all three still face
background/router validation. Add a corpus assertion in
`skopeo-profile-coverage.test.js` so a T1 label cannot silently create an
unusable button.

### Landmines

- Do not use “has required fields” as the predicate. Zillow has thirteen optional
  fields and `{}` is valid.
- Do not duplicate JSON Schema validation in the shell.
- Do not infer collectability from `paramSummary`; it is presentation data.
- There is no complete generic schema-driven input component in the repository.
  `pin-input.js` is numeric-specialized and is not an analog for this surface.
- Preserve secret handling: the consequence gate's label/secret/material path at
  `393-470` is the nearest safe-rendering pattern, not a full form renderer.

## Pattern 2: Resolve Handler Origin From the Registered Handler

### Proven pattern

`report-t1-readiness.mjs` already performs the required reconciliation. It loads
every registered head handler, seeds the same catalog used in production, resolves
the descriptor, then records the resolved handler origin separately from the
descriptor/service identity.

```js
// scripts/report-t1-readiness.mjs:783-800,1003-1014
const resolver = buildResolver(...);
const resolved = resolver.resolve(descriptor);
const runtimeOrigin = resolved.origin
  || resolved.recipe?.origin
  || descriptorOrigin;
```

`capability-catalog.js` establishes why the fields must remain separate:

```js
// extension/utils/capability-catalog.js:251-261,417-440,588-594
registerHandler(slug, { origin, params, descriptor })
seedHeadHandlers(...)
return { handler, origin, descriptor, ... }
```

The registered manifest contains concrete counterexamples to service-derived
origins: Slack uses `app.slack.com`, Notion uses `app.notion.com`, Wikipedia uses
`en.wikipedia.org`, and Zillow uses `www.zillow.com`.

### File assignments

- The generator should consume the trusted resolver result when emitting each
  capability's execution origin; the generated file only carries that result.
- The verifier should resolve the real catalog independently and compare the
  generated fact exactly once per capability.
- The projector should validate the emitted origin as a capability fact, not
  reconstruct it from `service`.
- The background should bind execution to the generated/resolved authority it
  receives, while the profile's admitted page origin continues to describe the
  page context.

### Regression pattern

Follow `verify-skopeo-profile-coverage.mjs:79-89` for exactly-once matching and
`coverage-report.mjs:222-255` for a real-corpus resolver walk. The test oracle
should compare every comparable Ready row with `resolved.origin`, then include
named regressions for the known `app.`, `www.`, and locale-subdomain cases. A
verifier that calls the generator's `exactOriginFor(service)` would only
self-confirm the current bug.

### Landmines

- `scripts/generate-skopeo-profile-index.mjs:74-83` and
  `scripts/verify-skopeo-profile-coverage.mjs:97-129` both derive
  `https://${service}`; neither is an independent authority.
- `skopeo-capability-projector.js:159-171` repeats the same conflation.
- `skopeo-profile-schema.js:125-135,200-230` intentionally constrains a profile's
  admitted page origin to its service. That contract is useful for page admission
  but must not be copied for handler execution origins.
- Never parse the private handler manifest as the production truth when the
  catalog's public `resolve` path is available.

## Pattern 3: Use One Consequence Schema and Target Contract

### Proven pattern

The router is the canonical argument validator; the consequence gate is the
authorization and safe-materialization boundary. They must interpret the same
resolved handler schema rather than maintaining incompatible schema subsets.

```js
// extension/utils/capability-router.js:102-128
const schema = this._handlerParamsSchema(entry);
const result = this._paramsValidator.validate(schema, params);

// extension/utils/skopeo-consequence-gate.js:532-593
buildAssessment(request, authority) // readiness, resolution, schema, args,
                                    // target, and consequence material
```

For target authority, the closest existing repository pattern is the anchor
registry: accept only closed semantic fields and require the semantic proof to
match the immutable descriptor before committing an effect.

```js
// extension/content/skopeo-anchor-registry.js:388-450
semanticProofMatchesDescriptor(...)
withdrawFirst(...)
commitImmutableTuple(...)
```

For lifecycle, preserve the gate's current order: recheck binding/authority,
consume the one-shot token synchronously, invoke the sole router, then recheck
epoch/binding/authority after the await (`skopeo-consequence-gate.js:705-776`).

### File assignments

- The generator/verifier own corpus-time compatibility: a row must not be emitted
  as an actionable Ready consequence if the shared schema/target contract cannot
  represent its real handler contract.
- The consequence gate owns runtime confirmation, target extraction, safe labels,
  materiality, and one-shot dispatch.
- The runtime owns collection and pending binding, but cannot weaken the gate.
- The generated index/projected row carry data only; no executable validators or
  target resolvers belong there.

### Concrete corpus hazards

- `skopeo-consequence-gate.js:28-32` omits the real Slack `channel` target role.
- `normalizeProperty` at `264-303` accepts only primitive property types, while
  Notion Ready writes include nested `properties` objects
  (`extension/catalog/handlers/notion.js:84-140`).
- `normalizeParamsSchema` at `305-339` and `projectedSummaryMatches` at `349-354`
  compare order-sensitive arrays, while the generator's summary sorts names.
- Slack's `postMessage` contract is `channel` + `text`
  (`extension/catalog/handlers/slack.js:99-107,525-543`).

These handler files are authority references, not part of the confirmed touch
set: do not rewrite valid handler contracts merely to fit the HUD gate.

### Regression pattern

Keep the current synthetic matrix for narrow failure diagnostics, then add a real
corpus sweep that resolves each Ready write through the production catalog and
passes the same schema/target compatibility function used by generation/runtime.
Add focused Notion and Slack cases, and retain the deferred-router assertion from
`skopeo-consequence-gate.test.js:600-628`: one confirmation produces exactly one
router call and one audit record even while the promise is pending.

### Landmines

- Do not “fix” order mismatches by sorting only one side of a comparison.
- Do not maintain separate generation, projection, and gate vocabularies without
  a contract test that proves they accept the same corpus.
- Do not weaken target checks to “any first string argument.” Target role is
  authority data and must be explicit and closed.
- Do not broaden the gate by bypassing the existing router; D-08 requires all
  execution to use that chokepoint.

## Pattern 4: Bound Presentation, Preserve Full Authority

### Proven pattern

The projector intentionally caps presentation metadata (`MAX_PARAMS = 12`) while
the generator accepts a larger source summary. That cap is a UI concern. Full
schema identity needs a stable canonical authority pattern such as the generator's
existing catalog version:

```js
// scripts/generate-skopeo-profile-index.mjs:46-56,173-176
stableJson(value)
`sha256:${createHash('sha256').update(stableJson(value)).digest('hex')}`
```

The test-side lock pattern already exists for schema identity:

```js
// tests/recipe-schema-lock.test.js:80-95,123-130
stable(value)
schemaHash(schema)
assert.equal(actualHash, EXPECTED_SCHEMA_HASH)
```

Canonicalization is also established in
`capability-signature.js:70-96,277-294`, where sorted canonical bytes are bound
into a signed payload. Use these as authority/digest analogs; the bounded summary
remains display-only.

### File assignments

- The generator/generated index own canonical full-schema authority and bounded
  display metadata as distinct facts.
- The projector may cap/format the display summary, but must not rewrite the fact
  used to authorize arguments.
- The background should validate request args against full indexed/resolved
  authority after checking the immutable identity binding.
- Projection tests own the boundary between “safe to display” and “complete enough
  to authorize.”

### Concrete failure and regression pattern

`skopeo-capability-projector.js:232-255` truncates optional parameters and rewrites
the count. `background.js:775-792` then exact-compares that bounded row to the full
indexed summary before invoking the canonical validator. Zillow's real search
schema has thirteen optional fields, including `map_bounds`
(`extension/catalog/handlers/zillow.js:34-56,284-300`), so valid `{}` is rejected
before router validation.

Add two complementary tests:

1. project the real Zillow row and prove `{}` reaches the router exactly once;
2. mutate a full-schema field outside the twelve displayed names and prove the
   full authority identity changes even when the visible summary does not.

Retain existing `<= 12` display assertions. The fix is not to expose the entire
schema in content/UI messages.

### Landmines

- A count plus twelve names is not a schema and cannot authorize arguments.
- Do not compare a lossy projection byte-for-byte with its full source.
- Use one canonical serializer everywhere a digest is compared; plain
  `JSON.stringify` over construction-order objects is not that contract.
- Keep the full authority in trusted generated/background data, not mutable DOM or
  shell state.

## Pattern 5: Per-Tab, Per-Generation Newest-Wins Route Sequencing

### Proven pattern

The sidepanel controller already implements the required concurrency discipline:
capture a monotonic request token before work, keep the latest token per lane,
keep a monotonic generation floor per tab, and check both after every await.

```js
// extension/ui/sidepanel.js:81-139
_requestSerial
_latestRequestByLane
_highestGenerationByTab
captureRequest(tabId, lane)
requestIsCurrent(request)
acceptGeneration(tabId, generation)
```

The background action controller provides the matching per-tab/generation
lifecycle shape: controller entries contain generation, abort controller,
projection/authority, gate, and one-shot token state
(`background.js:941-1075,1477-1604`). Same-document routing should follow that
existing ownership model rather than introduce global ordering.

### File assignments

- `background.js` owns route request sequencing because both independent URL
  change handlers enter there. The request identity must be captured before the
  first asynchronous boundary and checked before any completion mutates session
  state.
- `skopeo-session-lifecycle.test.js` proves content runtime state follows the
  accepted route generation.
- `skopeo-sidepanel-command.test.js` provides the production controller harness,
  deferred promises, and per-tab concurrency oracle.

### Regression pattern

Extend the production route harness rather than testing a detached helper:

```text
tab T starts route request R1
tab T starts newer route request R2
resolve R2 first with generation G2 -> G2 becomes active
resolve R1 second with generation G1 -> no projection/session/terminal mutation
assert the G2 session remains active
```

Also interleave a second tab to prove lane isolation. Reuse `createDeferred` from
`skopeo-sidepanel-command.test.js:142-150` and the established “late A1 performs
zero writes after A2” assertion style at `1470-1549`. The current route oracle at
`2469-2548` is sequential and therefore cannot expose the race.

### Landmines

- `background.js:1658-1732` currently mutates projection before the awaited route
  result is known and treats a late non-increasing epoch as terminal-off. An
  obsolete completion should be inert, not a terminal transition.
- `tabs.onUpdated` invokes the same handler independently at `1799-1808`; local
  promise order is not serialization.
- Capture the route sequence before the first await and recheck after every await.
- Scope newest-wins state by tab and the current controller generation. A global
  counter would make unrelated tabs cancel each other.
- Keep terminal cleanup authoritative: accepted terminal events still abort owned
  work, advance epochs, clear pending actions, and withdraw UI.

## Shared Repository Conventions

### Closed, frozen, data-only modules

When a Skopeo data contract changes, follow the dual-export classic-script pattern
used by `skopeo-profile-schema.js:1-4,333-344` and the exact-key/deep-freeze pattern
at `75-123,264-330`. Generated/profile payloads remain JSON-compatible data with
bounded strings/arrays and no functions.

### Repeat authority checks across asynchronous boundaries

The runtime repeats tuple checks before and after render/action work
(`skopeo-runtime.js:726-757,827-914`), and the consequence gate repeats
epoch/binding/authority checks after router completion (`705-776`). Any new
argument-collection or route await follows the same pattern.

### Real-corpus tests complement synthetic state-machine tests

Synthetic gate/composer fixtures are useful for precise diagnostics but currently
encode the broken assumptions: zero-ish argument shapes, recognized synthetic
targets, and sequential routes. Corpus invariants belong in the generator/verifier
tests; one-shot and stale-result mechanics stay in focused unit/integration tests.

### Single source, independent verifier

The production fact should come from the catalog's resolver. The verifier should
re-resolve and compare it, not call a copied origin/actionability heuristic. This
matches the current generated-byte check at
`verify-skopeo-profile-coverage.mjs:257-295`: recompute from authoritative inputs,
then compare the artifact.

## No Complete Analog Found

Two parts have only partial precedents:

- There is no generic Skopeo JSON-Schema argument form. The nearest pieces are the
  shell's closed DOM/event patterns, the router's canonical validator, and the
  gate's safe label/secret renderer. Planning must define the supported collector
  subset explicitly rather than claiming an existing component can be reused.
- There is no committed descriptor-level target-role vocabulary that already
  covers every Ready consequence. The gate has a closed but incomplete vocabulary;
  the anchor registry supplies the authority-matching pattern, not the missing
  catalog metadata itself.

These gaps are reasons for explicit contracts and corpus tests, not reasons to
relax validation.

## Planning Checklist

- [ ] Generator uses the registered handler resolver and emits no service-derived
      execution origins.
- [ ] Verifier independently checks every comparable corpus row exactly once.
- [ ] Actionability reflects schema collectability; noncollectable rows use the
      existing static presentation path.
- [ ] Runtime transports real args and invalidates collection/pending state on all
      generation and terminal boundaries.
- [ ] Consequence generation and runtime share one schema/target compatibility
      contract while retaining router validation and one-shot confirmation.
- [ ] Bounded parameter summaries are never used as full argument authority.
- [ ] A stable full-schema identity detects drift hidden beyond display bounds.
- [ ] Same-tab route completions are newest-wins; obsolete completions are inert.
- [ ] Corpus tests cover known origin mismatches, all Ready consequences, and real
      Zillow `{}` dispatch.
- [ ] Deferred integration resolves the newer route first and proves the older
      reply cannot tear down the newer session.
