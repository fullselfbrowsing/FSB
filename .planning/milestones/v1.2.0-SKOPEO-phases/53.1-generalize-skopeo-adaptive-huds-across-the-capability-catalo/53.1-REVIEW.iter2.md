# Phase 53.1 Code Review

**Reviewed:** 2026-07-18T00:16:39Z
**Depth:** standard
**Diff base:** `eadb7da0264b9b3fce25601d8b016b4a70ffba56`
**Status:** issues_found

## Summary

Phase 53.1 is not release-ready. The production content runtime rejects every projection produced by the current projector, and the dynamic content stack also omits a module that the production context resolver requires. Those are independent startup failures: the first stops `skopeo:configure` today; after it is fixed, the second makes the initial context resolve as `projection-invalid` and tears the mounted runtime down.

The new action surface also exposes extension-owned forms and confirmation controls through an open ShadowRoot and accepts untrusted synthetic events. A script in the host page can therefore drive a currently open HUD through argument submission and write confirmation without a user activation. Two additional integration defects affect otherwise valid operations: accepted consequence text can exceed the composer's smaller bounds and silently produce no alertdialog, and successful read handlers lose all structured result data before reaching the app-specific renderer.

The focused test suite is green. Its integrated runtime fixture uses a hand-built pre-Plan-10 projection and stubbed resolver/composer, while the injection-list test codifies the missing dependency as the expected list. The consequence tests use short values, and shell tests intentionally expose the open root and dispatch synthetic events. Those tests therefore do not exercise the failures below.

## Blockers

### BL-01: The content runtime rejects every real current-service projection

**Classification:** BLOCKER — all explicit HUD starts fail at configure
**Files:** `extension/utils/skopeo-capability-projector.js:106-124`, `extension/utils/skopeo-capability-projector.js:735-780`, `extension/content/skopeo-runtime.js:13-24`, `extension/content/skopeo-runtime.js:140-240`, `extension/content/skopeo-runtime.js:289-293`, `extension/content/skopeo-runtime.js:1448-1458`, `extension/background.js:1252-1281`

**Evidence:** The authoritative projector's exact capability contract now includes `consequenceCompatible` and `consequenceDigest` for every row. Its actionability rules also admit consequence-compatible writes and six new consequence failure reasons. The background creates that real projection and sends it unchanged in `skopeo:configure`. The runtime maintains a separate, stale exact-key validator that omits both consequence fields, allows only the old four actionability reasons, and requires every source-ready write to remain `unsupported/consequence-contract-pending`. `hasExactOwnKeys` consequently rejects every production row before prepare. Even after merely adding the two keys, the stale write rules still reject the five Ready writes, and the runtime's field validator rejects optional `title` while the shared action-authority/projector intentionally permit it (`extension/utils/skopeo-action-authority.js:426-429`, `extension/utils/skopeo-capability-projector.js:350-357`).

A direct contract comparison against a real Notion projection produced:

```text
production extra keys vs runtime validator: ["consequenceCompatible","consequenceDigest"]
```

**Why tests miss it:** `tests/skopeo-session-lifecycle.test.js:258-304` constructs a legacy capability row without the consequence fields, and `prepareAndCommit` sends that fixture at `tests/skopeo-session-lifecycle.test.js:1563-1568`. Projector tests validate the production shape, but no test passes a real `createProjection(...)` result through the actual content runtime's configure/prepare/commit path.

**Remediation:** Remove the shadow projection schema from the runtime. Inject a bounded, content-safe projection validator (the existing projector module can validate without injecting the full generated index, or extract its pure validator), then add only the runtime-owned generation/current-origin checks. If duplication remains, update the complete Plan-10 contract together: exact fields, consequence reason set, compatible-write actionability, and optional-`title` parity. Add a production integration that creates real projections for a read-only app and `app.notion.com`, crosses the structured-clone boundary, and requires actual configure/prepare/commit success plus mutation negatives.

### BL-02: The injected content stack omits the projector required by the resolver

**Classification:** BLOCKER — startup fails after configure is repaired
**Files:** `extension/background.js:603-614`, `extension/content/skopeo-app-context-resolver.js:305-313`, `extension/content/skopeo-app-context-resolver.js:545-590`, `extension/content/skopeo-runtime.js:797-834`, `extension/content/skopeo-runtime.js:1551-1561`

**Evidence:** `SKOPEO_INJECTION_FILES` injects profile schema and action authority, then the context resolver, but never `utils/skopeo-capability-projector.js`. Service-worker imports do not populate the content script's isolated global. The production resolver explicitly requires `global.FsbSkopeoCapabilityProjector.validateProjection`; when absent, `projectionIsCoherent` returns false. `createResolver` captures that false state without throwing, so the runtime believes resolver setup succeeded, but the first `resolve()` returns `unsupported/projection-invalid`. Commit then calls `terminateOwner('failed-start')` after mounting.

**Why tests miss it:** `tests/skopeo-catalog-runtime.test.js:48-59` declares the same incomplete list as `EXPECTED_DYNAMIC_FILES` and asserts it is the “complete adaptive stack” at lines 110-113. Resolver unit tests import the projector into the Node global, while the runtime lifecycle harness substitutes its own resolver at `tests/skopeo-session-lifecycle.test.js:1418-1427`; neither reproduces the production isolated-world file list.

**Remediation:** Inject `utils/skopeo-capability-projector.js` after its schema/authority dependencies and before `skopeo-app-context-resolver.js`, or inject an extracted pure projection-validator module at that point. Do not inject the full generated catalog. Strengthen the dynamic-stack oracle by evaluating exactly the listed files in a fresh content-world global with no service-worker globals, then pass one real projection through commit and require a recognized context.

### BL-03: Host-page scripts can synthesize selections, form submission, and write confirmation

**Classification:** BLOCKER — explicit confirmation can be bypassed while the HUD is open
**Files:** `extension/content/skopeo-shell.js:1118-1155`, `extension/content/skopeo-shell.js:1269-1276`, `extension/content/skopeo-shell.js:1901-1918`, `extension/content/skopeo-shell.js:2043-2062`, `extension/content/skopeo-shell.js:2273-2319`

**Evidence:** The shell publishes a discoverable `[data-skopeo-shell-root]` host and attaches `{mode:'open'}`. Every action button installs an ordinary click listener, the argument form accepts any submit event, and the consequence confirm button accepts any click; none checks `event.isTrusted`. DOM is shared across Chrome's main and isolated worlds, so a host-page script can access `host.shadowRoot`, set form values, dispatch submit, and `.click()` confirm. The resulting background request still appears to come from the extension because the content runtime sends it, so sender-ID and tuple checks do not distinguish the synthetic page-driven activation. The open root also lets page scripts read values while the user is typing in an extension-owned form.

The current tests expose both halves of the issue: browser code directly reads `host.shadowRoot` (`tests/skopeo-browser-contract.test.js:223-224`), and shell tests dispatch synthetic click/submit events and expect action emission (`tests/skopeo-adaptive-composer.test.js:738-740`, `tests/skopeo-adaptive-composer.test.js:902-915`).

**Remediation:** Use a closed ShadowRoot and retain only the shell's private reference. Require trusted user activation for every state-changing UI boundary, especially capability selection, argument submit, and consequence confirm; keyboard activation from a real user remains trusted. Refactor tests to use a test-only shell handle or trusted browser input rather than production `shadowRoot` access. Add a local-Chrome security oracle that runs hostile main-world code after isolated-world injection and proves it cannot read collector values, locate internal controls, or cause any outbound read/consequence message, while real pointer and keyboard input still works.

## Warnings

### WR-01: Valid write arguments can open a gate token but fail to render any confirmation

**Classification:** WARNING — accepted boundary values strand the write flow
**Files:** `extension/catalog/skopeo-consequence-targets.js:10-48`, `extension/utils/skopeo-action-authority.js:59-67`, `extension/utils/skopeo-action-authority.js:946-998`, `extension/utils/skopeo-consequence-gate.js:4-8`, `extension/utils/skopeo-consequence-gate.js:366-405`, `extension/content/skopeo-adaptive-composer.js:5-9`, `extension/content/skopeo-adaptive-composer.js:782-804`, `extension/content/skopeo-adaptive-composer.js:861-871`, `extension/content/skopeo-runtime.js:994-1016`

**Evidence:** The trusted consequence contracts accept target/material values up to 128 or 256 characters. Materialization and the background gate accept an aggregate render up to 1024 characters, with target and parameter summary individually bounded at 1024. The composer independently caps the target at 80, the parameter summary at 512, and the final assembled dialog body at 512. These are not equivalent bounds.

Using the committed real `notion.update_page` contract with schema-valid maximum values produced a valid materialization with target length 137, parameter summary length 826, and total contract render length 995. The background gate accepts it, but `composer.compose(...)` returns a valid Focused model with `consequence:null` because `validConsequenceInput` rejects the target/summary. `openSelectedConsequence` has already retained the action token and treats `composeAndRender` as successful, leaving the user with no alertdialog and no visible confirm/cancel path.

**Remediation:** Define one end-to-end confirmation rendering contract and use it in compiler, materializer, gate, composer, and shell. Either lower trusted role/aggregate bounds to what the final dialog can display or raise the composer/body model bounds with verified layout behavior. Make the runtime retain an open token only when the composed model is actually `interstitial` with a non-null consequence; otherwise cancel the token and show a typed error. Add minimum/maximum boundary cases for all five real writes from argument parsing through actual shell alertdialog render.

### WR-02: Successful reads discard handler data before the app-specific renderer

**Classification:** WARNING — production result presentation is generic and data-free
**Files:** `extension/background.js:833-857`, `extension/content/skopeo-runtime.js:932-991`, `extension/content/skopeo-renderer-registry.js:10-45`, `tests/capability-router.test.js:445-479`

**Evidence:** `typedReadResult` examines only `success`, `code`, and optional `message`. On success it always produces one generic `notice` section and discards all other router-result fields. Real T1a router results can carry structured `data` (the in-scope router contract test returns `{data:{ok:true}}` at `tests/capability-router.test.js:469`), but that data never reaches `renderTypedResult`. Consequently the genre renderer's fact, list, table, timeline, and diff paths are unreachable from a production read; they are exercised only with hand-built typed-result fixtures.

**Remediation:** Add a trusted background-side result adaptation boundary keyed by an allowlisted capability/result contract. Convert handler output into bounded closed sections accepted by the renderer registry, reject unknown/oversized/secret-bearing structures, and preserve the existing same-tuple post-await checks. If a capability intentionally exposes only completion status, encode that explicitly rather than silently dropping an otherwise useful result. Add a production router-result test containing structured data and require the selected genre renderer to emit the corresponding safe atoms.
