# Phase 53.1: Catalog-Wide Adaptive HUDs - Research

**Researched:** 2026-07-16
**Scope:** Planning evidence for ADAPT-01 through ADAPT-10
**Overall confidence:** High for repository seams, lifecycle reuse, catalog coverage, and automated validation; medium for the final per-genre visual compositions until a Phase 53.1 UI design contract is approved; medium for live behavior on all third-party hosts until representative user-controlled UAT is recorded

<user_constraints>
## Locked Product Constraints

- Skopeo remains explicitly invoked. Catalog membership, navigation, page content, and capability availability must never activate it automatically.
- The minimum coverage boundary is the complete committed catalog: 2,314 descriptors, 128 app stems, and 129 distinct services at the current baseline.
- Drive/Docs vendor contracts are one deep capability pack, not Skopeo's product boundary.
- Each supported app needs a context-appropriate HUD composition selected from exact app identity, page genre, semantic entity, requested task/lens, capability readiness, and action risk.
- The implementation is one shared lifecycle, shell, primitive grammar, and versioned profile contract. It is not 129 app runtimes and not one Drive-shaped layout reused everywhere.
- Only proven executable capabilities may appear runnable. Guarded, UAT-needed, bridge-needed, blocked, degraded, learn-pending, and discovery-pending work must remain visibly non-executable.
- Write and destructive actions must retain the existing origin pin, origin classification, denylist, consent, confirmation, serialization, and audit chokepoints.
- App, descriptor, schema, route, and host-page data are untrusted. A HUD cannot invent app identity, semantic identity, capability readiness, results, anchors, or actions.
- The supplied HUD export is visual and interaction grammar. It is not production code and it does not approve every illustrated workflow.

### Planner discretion

- Exact bounded genre enum and the mapping of the 128 app stems into it, provided every service is covered and ambiguous pages fail quiet.
- Exact file names and internal split between generated profile data, background resolution, content-side composition, and app-specific adapters.
- Exact default profile fields and renderer vocabulary, provided the schema is closed, versioned, and independently testable.
- Exact representative browser/UAT app matrix, provided it spans every genre and risk class and never substitutes fixture evidence for live-host approval.

## Executive Recommendation

Add an adaptive layer around the existing Skopeo owner rather than generalizing the Drive router into a monolith:

```text
explicit tab invocation + current generation
  -> background exact-origin app resolver
  -> trusted catalog/profile projection for only the current service
  -> content-side genre/context resolver
  -> adaptive composer
       inputs: app profile + genre + stable entity evidence + task/lens
               + readiness-filtered capability groups + side-effect risk
       output: closed render model using the six shared primitives
  -> existing Skopeo shell and semantic-anchor registry

confirmed capability action
  -> internal background request carrying generation + exact tab/origin + slug + params
  -> existing FsbCapabilityRouter.invoke(...)
  -> existing origin pin / denylist / consent / serialization / audit path
```

Keep `skopeo-context-router.js` as the Drive/Docs deep-pack router already proven by Phase 53. Introduce a catalog-wide app/profile resolver in front of it. Profiles that have no stable entity adapter may still render a truthful ambient/focused capability surface, but they must not create anchored marks or entity chips from a path, label, selector, or visible text alone.

The design reference explicitly describes "one assistant, situation-specific instrumentation," six primitives, three initial genres, and a genre router. Its load-bearing rule is: no capability pack ships custom chrome. Phase 53.1 should implement custom composition and app-native semantics, not custom UI infrastructure.

## Existing Architecture to Preserve

### Explicit lifecycle and outer authority

`extension/background.js` owns the current per-tab Skopeo controller and injects, in order:

1. `content/skopeo-context-router.js`
2. `content/skopeo-anchor-registry.js`
3. `content/skopeo-shell.js`
4. `content/skopeo-runtime.js`

`extension/utils/skopeo-session-state.js` provides the `off -> starting -> active -> terminating -> off` reducer, positive-safe-integer generations, terminal tombstones, and admission rules. `extension/content/skopeo-runtime.js` repeats generation/context/identity/binding authority immediately before visual side effects and produces an exact eleven-category resource certificate at teardown.

Phase 53.1 must add configuration/profile authority inside the current generation. It must not create a parallel always-loaded observer, tab controller, or lifecycle store.

### Shared visual grammar

`extension/content/skopeo-shell.js` is already the one Shadow DOM shell. Its public constants and policies are authoritative:

- primitives: `anchor`, `chip`, `halo`, `rail`, `ghost`, `gate`
- attention: `ambient`, `anchored`, `focused`, `interstitial`
- ambient: rail only
- anchored: anchor, chip, rail, halo
- focused: anchor, chip, ghost
- interstitial: gate only

The shell already provides transactional surface staging, commit-time geometry validation, collision rollback, focus restoration, live-region announcements, reduced-motion handling, and exact resource teardown. Phase 53.1 should add a closed adaptive render model and renderer entry point without allowing profiles to inject DOM, HTML, CSS, callbacks, or arbitrary primitive combinations.

### Semantic identity and revocable bindings

`extension/content/skopeo-anchor-registry.js` already treats DOM bindings as revocable certificates over immutable identity. It limits descriptors to exact keys, bounded stable text, allowlisted identity/locator kinds, at most eight locators, and named validators. It rejects selector-shaped identity and locator values.

The current kinds are Drive/Docs-specific plus `opaque-target`. Catalog-wide work should introduce generic, closed concepts such as catalog app/page identity and adapter-owned app entity identity only when a trusted adapter can provide stable evidence. Generic pages without such evidence remain unanchored.

### Catalog and execution truth

The current catalog truth is split intentionally:

- `extension/catalog/recipe-index.generated.js`: 2,314 descriptor documents with `slug`, `service`, `description`, `actionVerb`, `sideEffectClass`, `backing`, and optional closed `params` schema.
- `extension/utils/capability-search.js`: origin-biased search and the runtime hit contract. Its current display readiness values are `t1-ready`, `t1-guarded-fail-closed`, `blocked`, `learn-pending`, and `discovery-pending`; only `t1-ready` sets `invocable: true`.
- `scripts/report-t1-terminal-states.mjs`: the fuller terminal-state model used by milestone evidence: `t1-ready`, `guarded-fail-closed`, `blocked`, `bridge-needed`, `uat-needed`, and `degraded-discovery-pending`, with `executionEnabled` true only for `t1-ready`.
- `extension/utils/capability-catalog.js`: authoritative slug-to-tier resolver.
- `extension/utils/capability-router.js`: the one invoke engine shared by MCP and autopilot, including origin pinning, classification, denylist, consent, audit, recipe/handler dispatch, and typed pending/error results.

Do not create another readiness table or invoke path for Skopeo. Expose/reuse a pure readiness projection from the catalog/search seam, and generate any richer terminal-state metadata from the same reporting sources at build time.

### Existing verification seams

- `tests/skopeo-session-lifecycle.test.js`: generation, stale work, injection, teardown, and integration harness.
- `tests/skopeo-shell-contract.test.js`: primitive policy, focus, geometry, staged rendering, and exact-zero resources.
- `tests/skopeo-context-router.test.js`: exact-origin, closed route result, and hostile input controls.
- `tests/skopeo-anchor-registry.test.js`: final tuple authority, withdraw-first ordering, ABA, and bounded observers.
- `tests/skopeo-browser-contract.test.js`: real local-Chrome geometry, accessibility, production injection order, semantic churn, and 100-cycle closure.
- `tests/capability-search-eval.test.js`, `tests/coverage-report.test.js`, and `tests/t1-terminal-states.test.js`: catalog ranking, full-corpus completeness, and readiness/terminal-state truth.
- `npm run validate:extension`: extension syntax, catalog integrity, readiness, origin, classification, and evidence gates.

## Recommended Contracts and File Seams

The planner should verify exact names against neighboring conventions, but preserve these responsibilities.

### 1. Versioned app-profile schema and generated registry

Recommended sources:

- `catalog/skopeo/app-profiles.json` or one data file per profile/genre for curated app semantics and overrides.
- `extension/utils/skopeo-profile-schema.js` for pure exact-key validation and normalization.
- `scripts/generate-skopeo-profile-index.mjs` to join curated profiles with the committed descriptor corpus.
- `extension/catalog/skopeo-profile-index.generated.js` as pure bundled data consumed at runtime.

A normalized profile should contain only bounded data, for example:

```js
{
  schemaVersion: 1,
  appStem: 'github',
  serviceHosts: ['github.com'],
  allowedOrigins: ['https://github.com'],
  defaultGenre: 'worklist',
  entityVocabulary: { singular: 'repository', plural: 'repositories' },
  capabilityGroups: [{ id: 'issues', label: 'Issues', slugPrefixes: ['github.issues.'] }],
  adapterId: 'github',
  rendererId: 'worklist-default',
  attentionBudget: 'anchored'
}
```

Profiles contain identifiers and presentation data only. They may not contain executable code, selectors, arbitrary HTML/CSS, remote URLs, model prompts, or functions. Adapter and renderer IDs resolve only to bundled allowlisted modules.

`appStem`, `serviceHost`, and `origin` are different concepts. The current corpus has 128 stems but 129 services, so coverage and runtime lookup must not collapse them. Origin comparison must use parsed exact host/origin rules, never substring containment (`x.com` versus `netflix.com` is an existing regression precedent).

### 2. Background app/capability projection

Add a pure background-side resolver that accepts the current tab's exact URL/origin and current catalog data and returns a frozen, closed projection for the one current app/service. The projection should include:

- profile identity and version
- exact admitted origin/service/stem
- default genre and allowed adapter/renderer IDs
- grouped current-service capabilities with bounded labels and params schema summaries
- canonical readiness/terminal status and `invocable` boolean
- side-effect class (`read`, `write`, or `destructive`)

Do not inject the complete 2,314-row catalog into every page if a current-service projection is sufficient. Do not cache a projection across tab, origin, catalog version, or Skopeo generation boundaries.

### 3. Closed catalog-wide context/genre resolver

Create a content-side app-context resolver separate from the Phase 53 Drive contract router. Its result should be an exhaustive union such as:

- `recognized`: exact app/profile identity, genre, task/lens, optional trusted semantic entity, evidence
- `uncertain`: reason, retryability, no semantic entity
- `unsupported`: reason, no semantic entity

Exact origin and signed/bundled profile identity can prove the app. Page genre may begin with a trusted profile default and be refined only by allowlisted adapter evidence. Visible text, CSS classes, list position, or path alone cannot prove a stable entity. Drive/Docs profiles may delegate to the existing deep router.

Recommended bounded genres, to be finalized by UI-SPEC, are:

| Genre | Typical catalog families | Default attention intent |
|-------|--------------------------|--------------------------|
| reader/knowledge | articles, documentation, wikis | anchored |
| communication | inboxes, threads, chat, social messaging | anchored |
| document/editor | Docs, Word, design/editor surfaces | anchored or focused |
| worklist/record | project management, issues, CRM, tables | anchored |
| dashboard/admin | analytics, cloud, observability, finance dashboards | ambient |
| transactional | commerce, travel, food, account-changing flows | interstitial only at consequence |
| media/feed | video, social feeds, discovery surfaces | ambient or anchored |
| generic-app | safe baseline when no deeper genre adapter is proven | ambient |

Genre is an attention/composition policy, not an execution permission and not a substitute for exact app identity.

### 4. Adaptive composer and closed render model

Add a pure composer whose input is normalized profile + resolved context + requested lens/task + readiness-filtered capabilities. Its output should declare:

- attention level
- allowed primitives selected from the shell constants
- bounded copy tokens/labels
- capability groups and display states
- optional stable entity/anchor descriptor reference
- consequence model only for a selected write/destructive action

The composer must enforce the existing `ATTENTION_POLICY`; a profile cannot request an illegal primitive/attention combination. Halos require a validated anomaly signal, ghosting is temporary and reversible, and gates require an explicit selected consequential action. An app with no stable entity adapter can use ambient/focused surfaces but cannot emit anchored marks or chips.

### 5. Bundled adapters and renderers

Use a small registry of bundled adapter/renderer modules keyed by allowlisted IDs. Most apps should use genre defaults plus data-only profile vocabulary. Add app-specific adapters only where stable semantic evidence or custom result shape truly exists. The core receives normalized values, not host nodes or callbacks from profile data.

The first implementation matrix should prove:

- one generic app using catalog-only ambient composition
- one reader/knowledge profile
- one communication/worklist profile with stable adapter evidence
- one dashboard profile with sparse ambient attention
- one transactional profile with a consequence gate
- Drive/Docs delegation preserving all Phase 53 behavior

Full-catalog data coverage is mandatory even though browser mechanics are sampled by genre.

### 6. Consequence-gate execution adapter

The HUD should never call a handler, recipe, fetch primitive, or page action directly. A confirmed gate emits one internal request with current Skopeo generation, tab/origin authority, slug, and schema-validated params. Background rechecks the current tab/origin and delegates to `FsbCapabilityRouter.invoke`.

The adapter must:

- reject every readiness state except `t1-ready`
- show exact target, effect, side-effect class, and material params before confirmation
- prevent double-submit and stale confirmation after generation/origin/context changes
- preserve the capability router's existing typed pending/error response
- render results as text/data through an allowlisted renderer
- retain the router's origin, denylist, consent, audit, and serialization behavior as the final authority

## Security and Failure Analysis

| Threat | Required mitigation and test oracle |
|--------|-------------------------------------|
| Host/origin confusion | Parse URL and compare exact allowed origin/service relationships; near-neighbor and substring hosts must fail. |
| Profile drift or ambiguity | Full-corpus join requires exactly one resolution per service and fails CI on missing, duplicate, stale, or ambiguous origin mappings. |
| Malicious descriptor/profile strings | Exact-key schemas, length/count caps, no remote refs/code, `textContent` rendering, and hostile Unicode/HTML/selector fixtures. |
| Invented semantic identity | Only bundled adapter evidence may create stable entity identity; generic/path/text-only contexts remain unanchored. |
| Readiness escalation | Runtime projection must be derived from the canonical readiness/terminal sources; every non-ready status has `invocable:false`. |
| Consent or denylist bypass | All execution reaches `FsbCapabilityRouter.invoke`; tests install existing chokepoint spies and prove one call after confirmation, zero before/cancel/stale. |
| Stale generation/context/profile | Repeat generation, profile version, exact origin, context epoch, semantic identity, and action token immediately before render and invoke. |
| Cross-tab/app leakage | Projections and selections are keyed by tab + generation + exact origin + catalog/profile version; account-independent UI state is not reused across them. |
| Host-page spoofing/collision | One Shadow shell, branded accessibility names, pointer-transparent geometry, commit-time collision checks, no host mutations, and exact teardown. |
| Double execution | One-shot action token, disabled pending gate, router serialization, and repeated-click/message tests produce exactly one invoke/audit attempt. |
| Page content as instruction | Content remains data in closed schemas; no profile/model/tool prompt is constructed from raw page text in this phase. |
| Catalog-scale denial of service | Current-service projection, bounded arrays/strings/schemas, deterministic grouping, cold-start size/time gates, and no per-mutation full-catalog scans. |

## Planning Dependencies and Suggested Boundaries

Recommended dependency order:

1. Profile schema, catalog join/generator, and full-corpus coverage gate.
2. Exact-origin background resolution and current-service readiness projection.
3. Catalog-wide context/genre contract and safe generic profile behavior.
4. Pure adaptive composer plus shell render-model extension.
5. Adapter/renderer registry and representative genre profiles, preserving Drive/Docs delegation.
6. Consequence-gate-to-existing-router integration.
7. Cross-genre accessibility, lifecycle, real-Chrome, catalog-scale, and adversarial closure.

Plans may parallelize profile/coverage and pure composition contracts after their shared schemas are fixed. Runtime integration must wait for both. Consequence execution must wait for canonical readiness projection and render/gate contracts. Browser closure must be last.

Do not plan Phase 54 corpus permissions, Graphify truth, contract lineage, cited ask, or alerts into Phase 53.1.

- After every task: run that task's focused test plus `node --check` for every changed classic-script JavaScript file. Target feedback under 15 seconds.
- After every plan: run all new Phase 53.1 focused tests and adjacent existing Skopeo/capability tests. Target feedback under 60 seconds excluding local Chrome.

- After runtime/browser plans: run `node tests/skopeo-browser-contract.test.js` with a real local Chrome executable; do not mark live third-party hosts approved from the fixture.
- Before phase verification: run all focused tests, `npm run validate:extension`, and `npm test`.
- No three consecutive implementation tasks may lack an automated focused command.

### Full-catalog proof

The coverage test must load the same committed `extension/catalog/recipe-index.generated.js` used by capability search. It should derive descriptor, stem, and service sets from data, then assert:

- every descriptor resolves to one app stem/service profile
- every distinct service resolves exactly once
- every current stem appears in at least one profile
- no profile references a missing stem/service or ambiguous origin
- profile generation is deterministic and byte-stable
- new catalog entries fail until they inherit an unambiguous safe default or receive an audited override
- all non-`t1-ready` states remain `invocable:false`

Current numeric counts are regression baselines, not the long-term completeness source. The set join is the durable gate.

### Representative genre/browser matrix

Automated fixtures should cover reader, communication, editor, worklist, dashboard/admin, transactional, media/feed, generic-app, and Drive/Docs deep-pack delegation. For each fixture assert:

- explicit invocation only
- exact app/profile/genre selection
- expected sparse primitive set and attention ceiling
- zero irrelevant primitives
- no anchored output without stable identity evidence
- current origin/service capability filtering
- keyboard and screen-reader names/roles
- host controls remain usable and unobscured
- resize/zoom/SPA/row-reuse/stale-result withdrawal
- exact eleven-category zero after kill and repeated cycles

### Adversarial controls

Include weakened-oracle tests proving the suite detects: near-neighbor origin admission, missing profile coverage, duplicate service mapping, descriptor readiness promotion, illegal primitive/attention combinations, raw HTML rendering, selector-shaped identity, stale generation/profile action, direct router bypass, double execution, and teardown/resource leakage.

### Manual-only evidence

Live current-host UAT remains required for at least one user-controlled non-sensitive app per genre plus sensitive/transactional canaries where authorization permits. Record:

- actual host control coexistence and geometry
- keyboard, zoom, reduced motion, and VoiceOver behavior
- exact-origin/profile resolution through SPA navigation
- capability/result shapes from the user's existing session without storing secrets
- confirmation and honest non-ready states
- unsupported coverage and host drift rather than inferred passes

Automated coverage may be Nyquist-compliant while live approval remains partial. The validation artifact must keep those states separate.

## Planning Risks and Resolutions

1. **UI contract missing:** This phase decides app/genre composition and must run `$gsd-ui-phase 53.1` before executable plans are finalized. Research can define contracts, but it cannot choose final layouts, copy hierarchy, breakpoints, and interaction transitions on the user's behalf.
2. **Catalog count versus service identity:** Public copy says 128 apps while the report yields 129 services. Plans must gate on both sets and never use one count as a substitute for the other.
3. **Readiness truth is currently split:** The interactive search surface has five runtime statuses while terminal-state evidence has richer states. Plans must create one derived presentation contract without duplicating or weakening execution truth.
4. **Current router is Drive-specific:** Rewriting it in place risks invalidating completed Phase 53. Add a general app/profile layer and delegate to the existing deep router.
5. **Custom does not mean arbitrary:** Profiles need app-native vocabulary and behavior but cannot inject code or chrome. The closed composer is the customization boundary.
6. **Full live testing is impractical in one phase:** Guarantee data/profile coverage across every service automatically, then use a declared cross-genre live matrix and record the remaining host-specific evidence honestly.

## Confidence Assessment

- **High:** lifecycle reuse, shell grammar, profile/catalog join, readiness honesty, execution chokepoint, generated-data coverage, and automated test seams.
- **Medium-high:** generic genre/profile architecture and representative adapters.
- **Medium until UI-SPEC:** exact composition per genre, default lens/task interaction, copy hierarchy, and responsive behavior.
- **Human-needed:** current third-party host geometry, authenticated capability shapes, sensitive transactional confirmation, and VoiceOver across representative live apps.
