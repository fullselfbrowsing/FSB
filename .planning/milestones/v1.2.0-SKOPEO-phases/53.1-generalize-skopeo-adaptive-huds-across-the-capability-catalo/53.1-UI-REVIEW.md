# Phase 53.1 — UI Review

**Audited:** 2026-07-18
**Baseline:** 53.1-UI-SPEC.md (approved)
**Screenshots:** Not captured. Playwright-MCP was unavailable; port 3000 returned a non-auditable HTTP 401, ports 5173 and 8080 were unreachable, and Phase 53.1 is an unpacked Chrome-extension surface rather than a served page. No server was started.
**Audit mode:** Code-only. Findings distinguish code-verifiable defects from live-host observations that remain unverified.

---

## Pillar Scores

| Pillar | Score | Key Finding |
|--------|-------|-------------|
| 1. Copywriting | 1/4 | 118 of 130 generated profiles render the literal identity “Supported app,” so most catalog HUDs cannot name the exact app or use app-native nouns; consequence results can also expose raw slugs and internal router language. |
| 2. Visuals | 2/4 | A collision-selected 88px compact lens at a wide viewport still renders the full label and metadata that compact mode must omit. |
| 3. Color | 2/4 | Muted status/detail text on the orange primary action measures only 1.04:1 contrast, and destructive/selected semantics do not use their contracted tokens consistently. |
| 4. Typography | 2/4 | Several new labels, headings, details, chips, and errors use family/size/weight combinations outside the four approved semantic roles. |
| 5. Spacing | 3/4 | Argument collection introduces 12px gap and padding even though the approved spacing scale has no 12px token or exception. |
| 6. Experience Design | 2/4 | App scope is ambiguous across most profiles, consequence pending/stale feedback is not rendered, and boolean argument targets are only 20px tall. |

**Overall: 12/24**

**Severity summary:** 1 BLOCKER and 8 WARNING findings. The exact-app-identity defect is a BLOCKER because it breaks the central catalog-wide scope/safety promise for the majority of generated profiles; the remaining findings are contract, accessibility, or confidence degradations.

---

## Top 3 Priority Fixes

1. **Give every admitted profile a trusted exact app identity and app-native vocabulary, or fail quiet** — Replace the shared `Supported app`/`app`/`item` defaults with bounded generated or authored display names, page/entity nouns, and useful group labels that are tied to the exact catalog identity. Do not derive visible identity from the current hostname. Add a coverage gate that rejects a recognized profile whose visible app identity is still the shared placeholder.
2. **Restore AA contrast and risk semantics on emphasized controls** — Override status/detail descendants of the orange primary row to `#0d0a09`, keep destructive gate text/eyebrow red rather than orange, and give the selected entity chip its reserved accent signal. Assert computed contrast and forced-colors behavior in a real browser.
3. **Render the full consequence lifecycle with human action labels** — On confirmation, replace the confirm label with the composed gerund pending label while controls remain unavailable; on context expiry, present the exact stale copy before returning safely. Carry the selected catalog action label—not its slug—through success and typed failure, and remove the user-visible “capability router” implementation wording.

## Detailed Findings

### Pillar 1: Copywriting (1/4)

- **BLOCKER — code-verifiable:** The shared profile default is `displayName: "Supported app"`, `pageNoun: "app"`, generic `item/items`, and no capability groups (catalog/skopeo/app-profiles.json:4-17). Unauthored stem/service pairs inherit that object unchanged during generation (scripts/generate-skopeo-profile-index.mjs:369-397), and empty groups become the visible label `Capabilities` (extension/utils/skopeo-capability-projector.js:612-650). The projection then passes the placeholder display name into app context (extension/content/skopeo-app-context-resolver.js:347-353), and the composer emits it directly as `Skopeo · Supported app`, `Open Supported app actions`, and the region name (extension/content/skopeo-adaptive-composer.js:692-703). A deterministic count over extension/catalog/skopeo-profile-index.generated.js found 118/130 profiles with that placeholder, covering 2,088/2,314 capability rows and 1,158 invocable rows. This contradicts the exact-app and app-native lens/card contract (53.1-UI-SPEC.md:216-245) and prevents a user from verifying which app an action HUD is scoped to.
- **WARNING — code-verifiable:** Argument collection composes and validates the literal `Cancel` label (extension/content/skopeo-adaptive-composer.js:728-742,990-1014), and the shell renders it as the secondary form action (extension/content/skopeo-shell.js:2185-2201). Bare `Cancel` is explicitly prohibited by the action grammar (53.1-UI-SPEC.md:287-289). Use a scoped label such as `Back to {App display name} actions` or `Keep reviewing {specific action}`.
- **WARNING — code-verifiable:** The composer creates the required gerund pending and exact stale labels (extension/content/skopeo-adaptive-composer.js:814-830), but neither label has a rendering consumer; confirmation only disables the two buttons and dispatches (extension/content/skopeo-shell.js:2459-2475). Completion then substitutes `selectedActionSlug` for the human action label and exposes “completed through the capability router” in the visible result (extension/content/skopeo-runtime.js:902-921). The failure path can therefore produce copy such as `notion.update_page didn’t finish`, despite the prohibition on raw slugs and the requirement for a specific projected action label (53.1-UI-SPEC.md:264-297). Preserve the selected row label through invocation and render the pending/stale contract instead of orphaning it in the model.

### Pillar 2: Visuals (2/4)

- **WARNING — code-verifiable:** Compact mode is a normal wide-viewport fallback after all full-lens corners collide (extension/content/skopeo-shell.js:1075-1103), but applying it only sets `data-placement-mode="compact"` and width 88px (extension/content/skopeo-shell.js:1491-1510). The lens always renders glyph, full visible label, metadata, and a 32px close control (extension/content/skopeo-shell.js:1962-1991); metadata is hidden only by `max-width: 479px`, with no placement-mode rule (extension/content/skopeo-shell.js:525-530). This violates the required compact glyph/open/close composition and visual metadata omission (53.1-UI-SPEC.md:216-227), and it can paint content beyond the collision-tested 88px rectangle. The current compact test checks only the mode attribute and outer width (tests/skopeo-shell-contract.test.js:1057-1066). Hide nonessential visible children whenever `data-placement-mode="compact"`, retain full accessible text, and test computed child bounds/overflow at both sides of 480px.
- **Contract evidence:** The adaptive surface otherwise keeps the approved shared shell primitives, explicit Ambient/Anchored/Focused/Interstitial levels, safe-first gate source order, and narrow stacked actions/fact-list fallback. These mechanics are exercised by the focused composer, shell, accessibility, and gate suites.

### Pillar 3: Color (2/4)

- **WARNING — code-verifiable:** `.skopeo-ready-primary` sets the parent to orange with dark text, but `.skopeo-row-status` and `.skopeo-row-detail` override descendants to muted `#a99283` (extension/content/skopeo-shell.js:447-471). That muted text on `#ff6b35` measures 1.04:1, while the required `#0d0a09` measures 6.96:1. This fails WCAG AA and the explicit orange-filled-control rule (53.1-UI-SPEC.md:102-127). Apply the dark foreground to every visible child of the primary row and cover it with a computed-style contrast assertion.
- **WARNING — code-verifiable:** Every `.skopeo-eyebrow`, including the destructive gate eyebrow, is forced orange (extension/content/skopeo-shell.js:386-395), even though the gate receives a destructive token only on its parent (extension/content/skopeo-shell.js:515,2441-2453). Conversely, `.skopeo-entity-label` receives only neutral `.skopeo-chip` styling and has no selected-accent rule (extension/content/skopeo-shell.js:320-331,1993-2001). The contract reserves orange for the selected entity chip and forbids orange from softening destructive consequences (53.1-UI-SPEC.md:115-127,319). Add explicit selected-chip and destructive-eyebrow selectors rather than relying on an all-eyebrow accent.

### Pillar 4: Typography (2/4)

- **WARNING — code-verifiable:** The approved roles are exactly 11/700 mono, 12/400 mono, 14/400 sans, and 16/700 sans (53.1-UI-SPEC.md:87-98). The adaptive shell instead uses 14/700 sans for the lens label, section/group/atom headings, and argument labels; 12px sans for the selected entity chip, row detail, and argument error (extension/content/skopeo-shell.js:233-250,320-331,440-497). These combinations use allowed raw sizes and weights but not the approved semantic pairings, producing inconsistent hierarchy across genres. Map each element to one existing role instead of creating implicit 14/700 and 12px-sans variants.

### Pillar 5: Spacing (3/4)

- **WARNING — code-verifiable:** The new argument form uses `gap: 12px` and `padding: 12px` (extension/content/skopeo-shell.js:472-480). The Phase 53.1 scale permits only 4, 8, 16, 24, 32, 48, and 64px spacing and explicitly declares no exceptions (53.1-UI-SPEC.md:69-83). Replace those values with the nearest semantic tokens—typically 8px field rhythm and 16px form padding—and add a bounded style-token check for Phase 53.1 UI additions.
- **Contract evidence:** Capability rows, group separation, action gaps, and narrow 16px insets otherwise use the declared scale consistently.

### Pillar 6: Experience Design (2/4)

- **WARNING — code-verifiable:** Boolean argument controls explicitly shrink from the standard 40px control to 20×20px (extension/content/skopeo-shell.js:485-495). The adjacent label is associated correctly (extension/content/skopeo-shell.js:2118-2173), but neither the checkbox row nor label has a 32px minimum target, while the contract requires inherited 32px compact, 40px standard, or 44px switch target geometry (53.1-UI-SPEC.md:69-83). Give the combined checkbox/label row a tested minimum target height and preserve visible focus on the native checkbox.
- **Cross-pillar impact:** Ambiguous app identity prevents users from confirming action scope, and the non-rendered pending/stale states leave a safety-critical write flow without the promised progress/expiry feedback. Those are the principal reasons this pillar is below 3/4 despite strong explicit-transition, focus-entry, cancellation, authority, and exactly-once mechanics.
- **Live evidence boundary — unverified:** 53.1-HUMAN-UAT.md remains `status: human_needed` and `live_approved: false`, with every cell across all nine genre rows still `human_needed` (53.1-HUMAN-UAT.md:1-45). Real app terminology, authenticated readiness, host-control coexistence, SPA/origin drift, keyboard/200% zoom, reduced motion, VoiceOver, and transactional canary behavior remain needs_human_review. This audit does not convert local fixtures or source inspection into live approval.

## Audit Coverage and Limitations

- The required `.planning/ui-reviews/.gitignore` screenshot guard exists and covers common raster formats. No screenshot artifact was created.
- Playwright-MCP was unavailable. No existing auditable Phase 53.1 server was reachable on the permitted ports, and no server was started.
- Focused checks run during this audit all passed: `skopeo-adaptive-composer`, `skopeo-shell-contract`, `skopeo-accessibility`, and `skopeo-consequence-gate`. Passing confirms the mechanics those suites assert; it does not cover the catalog placeholder, primary-row descendant contrast, placement-mode child visibility, or actual consumption of pending/stale copy.
- Registry safety was not applicable: `components.json` is absent and the approved UI specification declares no shadcn or third-party registry dependency.
- The prior automated verification reports `human_needed`, `live_approved: false`, and nine live rows outstanding (53.1-VERIFICATION.md:1-19). This review preserves that evidence boundary.
