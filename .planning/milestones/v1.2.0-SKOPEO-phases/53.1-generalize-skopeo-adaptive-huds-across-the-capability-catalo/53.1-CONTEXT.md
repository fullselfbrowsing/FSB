# Phase 53.1: Generalize Skopeo Adaptive HUDs Across the Capability Catalog - Context

**Gathered:** 2026-07-16 (assumptions mode)
**Status:** Ready for planning

<domain>
## Phase Boundary

Turn the proven explicitly invoked Skopeo lifecycle, shared primitive shell, and revocable semantic-binding foundation into a catalog-wide adaptive HUD platform. Phase 53.1 resolves the current exact-origin catalog app, page genre, verified entity evidence, requested task/lens, capability readiness, and action risk into one sparse app-appropriate composition or a concise fail-quiet state. It covers the complete committed catalog profile contract and representative cross-genre runtime proof without adding an always-on observer, divergent app runtimes, new arbitrary chrome, Phase 54 corpus permissions, Graphify truth, contract intelligence, cited ask, or alerts.

</domain>

<decisions>
## Implementation Decisions

### Profile, service, and origin authority

- **D-01:** Use one versioned, data-only app-profile registry. Profiles contain bounded identifiers, vocabulary, capability grouping, attention defaults, and allowlisted adapter/renderer IDs; they never contain executable code, selectors, HTML, CSS, prompts, callbacks, or remote assets.
- **D-02:** Keep app stem, catalog service, exact admitted origin, and profile version as distinct keys. Stem-only identity, hostname substrings, visible host branding, page titles, and content-side inference cannot admit an app or merge two services.
- **D-03:** Background authority resolves the current tab's exact origin and projects only the active service/profile plus its bounded current-service capability surface into the current Skopeo generation. Do not inject the full 2,314-descriptor catalog into every page or reuse a projection across tab, origin, generation, or profile-version boundaries.

### Context and adaptive composition boundary

- **D-04:** Add the catalog-wide app/genre/context resolver and adaptive composer around the existing Skopeo owner, ahead of the Phase 53 Drive/Docs router. Drive/Docs delegates to that proven deep adapter unchanged instead of being generalized in place.
- **D-05:** Generic profiles may provide an exact app identity, app-native nouns, grouped capabilities, and Ambient/Focused app-level surfaces. They remain unanchored unless a bundled allowlisted adapter supplies current stable semantic evidence; URL paths, visible labels, CSS classes, list position, or DOM shape alone never create an entity.
- **D-06:** Preserve one lifecycle, one Shadow DOM shell, six primitives, four attention levels, and the approved Phase 53.1 closed renderer atoms. The composer may choose Ambient or Anchored after explicit invocation, but Focused requires an explicit Skopeo control and Interstitial requires selection of one ready consequential action.

### Readiness and consequence authority

- **D-07:** Consume one canonical readiness projection. Only `t1-ready` is actionable; guarded fail-closed, blocked, bridge-needed, UAT-needed, learn-pending, discovery-pending, degraded, and unsupported dispositions remain honest static statuses rather than disabled controls styled as nearly runnable.
- **D-08:** Confirmed write and destructive actions always return to background and delegate to the existing `FsbCapabilityRouter.invoke` chokepoint. Skopeo cannot call handlers, recipes, fetch primitives, page actions, or a parallel executor directly.
- **D-09:** A consequence gate names the exact target, effect, side-effect class, and material parameters, then rechecks generation, tab, exact origin, profile version, context epoch, semantic entity, readiness, and one-shot action token before invocation. Cancel, stale context, replacement, kill, and repeated submission produce zero or exactly one router/audit attempt as appropriate.

### Catalog coverage and runtime evidence

- **D-10:** The durable CI gate joins the committed descriptor corpus by descriptor, stem, and distinct service and requires exactly one profile or explicit safe disposition per service. The current 2,314 descriptors, 128 stems, and 129 services are regression baselines; missing, stale, duplicate, ambiguous-origin, and nondeterministic generated data fail the build.
- **D-11:** Prove composition and browser mechanics with deterministic fixtures spanning every approved genre plus Drive/Docs delegation. Keep automated full-catalog coverage, representative real-Chrome mechanics, and authorized live third-party-host approval as separate evidence states; fixtures never imply all-host live approval.
- **D-12:** Reuse the current generation, final-tuple authority, host-integrity, accessibility, collision, resource-ledger, and exact-zero teardown contracts. New profile/context/capability/action work is generation-owned, bounded, abortable, and incapable of repainting or executing after terminal state.

### The agent's Discretion

- Exact source file split between curated profile data, schema validation, deterministic generation, background projection, content-side resolver/composer, and bundled adapter/renderer registries.
- Exact bounded profile schema field names, schema-version migration shape, safe-default inheritance mechanics, and internal reason-code names, provided D-01 through D-03 and the full-corpus gate remain true.
- Exact representative services used for each approved genre fixture and authorized live-UAT matrix, provided every genre and risk class is covered and Drive/Docs regression remains explicit.
- Exact focused test commands and task/wave boundaries, provided the approved `53.1-VALIDATION.md` sampling and security requirements are preserved.

</decisions>

## Existing Code Insights

### Reusable Assets

- `extension/utils/skopeo-session-state.js` — Current-tab lifecycle reducer, monotonic generations, terminal tombstones, and message admission rules.
- `extension/background.js` — Exact tab/origin authority, current-generation controller, ordered dynamic injection, teardown certificate handling, and the natural owner for profile/capability projection.
- `extension/content/skopeo-context-router.js` — Completed Drive/Docs closed router to preserve as a deep adapter.
- `extension/content/skopeo-anchor-registry.js` — Immutable descriptors, revocable semantic bindings, final-tuple authority, bounded observers, and withdraw-first behavior.
- `extension/content/skopeo-shell.js` — Sole Shadow DOM shell, six primitives, attention policy, closed copy, collision/focus/accessibility behavior, and resource ledger.
- `extension/content/skopeo-runtime.js` — Generation-owned content coordinator and exact-zero teardown integration point.
- `extension/catalog/recipe-index.generated.js`, `extension/utils/capability-search.js`, and `extension/utils/capability-catalog.js` — Committed descriptor corpus, origin-biased discovery/readiness truth, and slug-to-tier catalog resolution.
- `extension/utils/capability-router.js`, `extension/utils/consent-policy-store.js`, `extension/utils/service-denylist.js`, and `extension/utils/audit-log.js` — Existing consequence execution, policy, consent, serialization, and audit chokepoints.
- `scripts/report-t1-terminal-states.mjs` and `scripts/coverage-report.mjs` — Current terminal-state and full-corpus evidence patterns that the profile coverage gate should derive from rather than duplicate.

### Established Patterns

- Extension runtime code uses bundled classic-script modules with frozen closed contracts and CommonJS test exports where needed; dynamic injection order is dependency-sensitive.
- Page-derived and catalog-derived values are exact-key, bounded, text-only data. Unknown values fail closed rather than widening enums or executing dynamic behavior.
- Background owns tab/origin/generation authority; content repeats authority immediately before visual side effects; the capability router repeats policy before execution.
- Generated catalog artifacts are deterministic committed data with build/test gates; runtime consumers use the same committed source rather than a hand-maintained shadow list.
- Verification uses standalone Node assertions, VM/fake-Chrome sandboxes, deterministic fixtures, a real local-Chrome contract, `npm run validate:extension`, and the full `npm test` chain.

### Integration Points

- Add schema/generator/profile data beside the existing catalog pipeline and register deterministic verification with extension validation.
- Extend background injection/configuration so the frozen current-service projection is prepared for the exact tab/generation before content composition.
- Add the general resolver/composer and bundled adapter/renderer registries around the existing Drive router, anchor registry, shell, and runtime rather than replacing them.
- Route confirmed gates through an internal background message carrying current authority into `FsbCapabilityRouter.invoke`.
- Register new focused Phase 53.1 tests before adjacent lifecycle/shell/browser regressions and preserve the final extension/full-suite gates.

<specifics>
## Specific Ideas

- “Custom HUD” means the composition, vocabulary, relevant capability groups, semantic evidence, and result presentation suit the current app and task; it does not mean 129 visual systems or 129 runtimes.
- Drive/Docs is one deep integration pack. The platform boundary is every supported catalog service, including safe generic profiles when no deeper semantic adapter is proven.
- Skopeo should interpret what is useful for the current situation while staying explicitly invoked, sparse, recognizable as Skopeo, and honest about everything it cannot verify or execute.
- The extra service beyond the 128 stems is a deliberate regression canary: coverage cannot treat stem count as service coverage.

</specifics>
