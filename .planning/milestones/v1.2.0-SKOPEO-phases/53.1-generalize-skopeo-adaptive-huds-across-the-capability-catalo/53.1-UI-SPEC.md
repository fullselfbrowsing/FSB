# Phase 53.1 — UI Design Contract

> Visual and interaction contract for an explicitly invoked, catalog-wide Skopeo HUD that adapts its composition and vocabulary to the current app, page genre, verified entity, requested lens, capability readiness, and action risk.

---

## Contract Intent and Boundary

Phase 53.1 turns the approved Phase 52 shell and Phase 53 semantic-binding contract into one adaptive HUD system for the complete committed capability catalog. The current baseline is 2,314 descriptors, 128 app stems, and 129 distinct services. Every current service receives a versioned data profile and a safe genre composition; browser mechanics are verified with representative genre fixtures and authorized live hosts.

Skopeo remains absent until the user explicitly invokes it for the current tab. Catalog membership, navigation, page content, capability readiness, alerts, and background work never activate Skopeo or raise its attention level. After invocation, Skopeo may open directly into Ambient or Anchored according to verified context. It may never enter Focused or Interstitial without an explicit Skopeo control activation.

This contract preserves one lifecycle, one Shadow DOM shell, one six-primitive grammar, one attention policy, and one consequence path. App profiles customize bounded vocabulary, capability grouping, stable semantic evidence, and allowlisted result renderers. They do not provide HTML, CSS, selectors, callbacks, prompts, remote assets, arbitrary components, or a second shell.

Drive and Docs remain a deep capability pack that delegates to the Phase 53 router and semantic-anchor registry. They are representative integrations, not Skopeo's product boundary. Phase 54 corpus permissions, Graphify truth, contract lineage, cited ask, alerts, drafting, and sending remain out of scope.

The supplied HUD board establishes the product principle “one assistant, situation-specific instrumentation.” It is a reference for grammar and intent, not production code or approval for illustrated actions.

## Shared Visual Grammar

The lens and focused card are shared shell chrome. The only capability primitives remain `anchor`, `chip`, `halo`, `rail`, `ghost`, and `gate`.

| Attention | Entry rule | Required/shared chrome | Allowed capability primitives | Prohibited |
|-----------|------------|------------------------|-------------------------------|------------|
| Ambient | Explicit invocation with exact app identity but no stable selected entity, or a profile whose safest default is overview | Compact/full lens, visible close, rail | `rail` | Anchor, chip, halo, ghost, gate, focus movement |
| Anchored | Explicit invocation plus stable adapter evidence for one relevant entity | Lens, visible close, rail | `anchor`, `chip`, optional `halo`, `rail` | Ghost, gate, automatic focus movement, guessed entity |
| Focused | User activates `Open {App} actions`, an entity chip, or a named capability group | Focused card, visible back/turn-off controls | `anchor`, `chip`, temporary `ghost` | Gate, unrelated anchors, automatic execution |
| Interstitial | User selects one ready write/destructive capability and current authority passes | One consequence gate with safe return first | `gate` only | Rail decoration, unrelated chips, multiple gates, background execution |

The composer may choose Ambient or Anchored as the first committed state after explicit invocation. It never chooses Focused or Interstitial automatically. It never escalates attention because of page content, a catalog update, a readiness change, a timer, a network response, or an alert.

### Sparse-composition rules

- Render the smallest composition that truthfully answers the current lens.
- Omit a primitive when its semantic prerequisite is absent; do not show disabled decorative placeholders.
- An anchor requires current stable identity and safe geometry. A chip requires the same identity but may survive a temporary geometry withdrawal only inside the focused Skopeo card, labelled as unanchored.
- A halo requires a bounded validated anomaly signal selected by the requested lens. It is never a confidence score, loading state, error, or generic highlight.
- Ghosting is temporary, reversible, pointer-transparent, and available only while Focused.
- A gate represents one selected consequence, not a generic confirmation pattern.
- Every composition includes a visible route back or turn-off action. The universal current-tab kill remains available with the inherited double-Escape behavior.

## App Profile Presentation Contract

A normalized profile may supply only bounded presentation data:

| Field | Presentation use | UI restriction |
|-------|------------------|----------------|
| App display name | Lens/card title and accessible name | Plain bounded text; cannot imitate host logos |
| Genre | Default composition and content order | One allowlisted genre below |
| Entity vocabulary | Singular/plural nouns such as `issue`, `message`, or `dashboard` | Plain bounded text; no markup or instruction text |
| Capability groups | Group ID, label, order, and slug membership | Closed list; empty groups are omitted |
| Adapter ID | Stable page/entity evidence | Bundled allowlist only; never shown as code |
| Renderer ID | Closed result presentation | Bundled allowlist only; no arbitrary HTML/CSS |
| Attention ceiling | Maximum default attention | `ambient` or `anchored`; never `focused`/`interstitial` by default |

Profile presentation is Skopeo-branded, not host-branded. Do not use host logos, brand colors, copied navigation shapes, or language implying that the host produced or approved the HUD.

### Closed content atoms

Focused/result surfaces may compose only these shared atoms inside the existing card:

- `section-heading`: bounded group or result label;
- `status-row`: label, text status, optional neutral detail;
- `capability-row`: specific action label, readiness text, optional parameter summary;
- `fact-list`: bounded label/value pairs;
- `item-list`: bounded text items with optional metadata;
- `compact-table`: bounded columns/rows; below 480px each row becomes a labelled fact list;
- `timeline`: ordered text events and timestamps;
- `diff`: bounded before/after text with explicit labels;
- `notice`: one informational, warning, or error message with a next step.

Every value is rendered through `textContent`. No raw HTML, Markdown execution, image URL, iframe, SVG string, remote icon, embedded form, script, CSS, or host node enters a renderer.

## Lens, Card, and Capability Anatomy

### Ambient/Anchored lens

| Element | Contract |
|---------|----------|
| Active glyph | One 8px orange glyph; decorative, with state included in the region name |
| Primary label | `Skopeo · {App display name}`; exact admitted app only |
| Metadata | `{App-native lens} · {N} ready`; omit visually in compact mode but retain in accessible description |
| Primary CTA | `Open {App display name} actions`; specific verb+noun accessible name |
| Close | `Turn off Skopeo` |
| Rail | Current-state geometry only; no decorative full-height glow |

The preferred full lens remains 240×40px. Compact mode remains 88×40px and shows glyph plus open/close controls; its accessible region name and descriptions retain app, lens, and readiness. If the exact app cannot be resolved, do not interpolate a hostname into the label.

### Entity chip

Visible pattern: `{Entity noun}: {bounded label}`. Accessible name: `Open actions for {entity noun} {bounded label}`. Secondary counts use metadata and never replace the entity label. If geometry becomes unsafe, withdraw the mark first; the chip also withdraws outside Focused. Inside Focused it may remain as `Previously selected {entity noun}; target is no longer verified` with all entity actions unavailable.

### Focused action card

| Order | Content |
|-------|---------|
| 1 | Micro eyebrow: exact app display name and app-native lens |
| 2 | Title: verified entity label, or `{App display name} actions` when no stable entity exists |
| 3 | One-line context/status description |
| 4 | Ready capability groups relevant to the current lens |
| 5 | Collapsed-by-default `Unavailable actions` status summary when non-ready capabilities exist |
| 6 | Optional closed result renderer after a selected read action completes |
| 7 | Back and `Turn off Skopeo in this tab` controls |

Only one ready action receives orange primary emphasis: the currently selected action or the profile's first lens-relevant read action. Other ready actions remain neutral. Write/destructive groups are visually separated after read groups and carry explicit `Changes data` or `Destructive` text before selection.

### Readiness presentation

| Canonical disposition | Visible status | Interaction |
|-----------------------|----------------|-------------|
| `t1-ready` | `Ready` | Specific action control may be activated |
| guarded fail-closed | `Unavailable safely` | Static status; explain that the execution path is not verified |
| blocked | `Blocked by policy` | Static status; name the safe next step when one exists |
| bridge-needed | `Connection required` | Static status; link only to an existing trusted setup surface if available |
| UAT-needed | `Needs verification` | Static status; never style as almost ready |
| learn-pending | `Learning pending` | Static status; no spinner or time promise |
| discovery-pending / degraded discovery | `Capability discovery pending` | Static status; explain that no action is available yet |
| unsupported | `Not supported in this view` | Static status; retain app/lens context without guessing |

Only `t1-ready` produces an actionable capability row. A disabled control must not be used to make another state look runnable; non-ready entries are status rows.

### Shared exact copy

| Element/state | Exact copy or closed template |
|---------------|-------------------------------|
| Lens label | `Skopeo · {App display name}` |
| Primary CTA | `Open {App display name} actions` |
| App-level focused title | `{App display name} actions` |
| Entity focused title | `{Entity noun}: {bounded entity label}` |
| No ready actions heading | `No verified actions here` |
| No ready actions body | `Skopeo found no ready capabilities for this {page noun}. Change the task lens or open another supported view.` |
| Uncertain heading | `Skopeo can’t verify this view.` |
| Uncertain body | `The page was left unchanged. Open another view or turn off Skopeo.` |
| Unsupported app heading | `Skopeo doesn’t support this app yet.` |
| Unsupported app body | `Nothing was added to the page. Turn off Skopeo or open a supported app.` |
| Target withdrawn | `Skopeo can’t verify this {entity noun} anymore. Entity actions were removed.` |
| Capability failure | `{Specific action label} didn’t finish. {Typed safe recovery step}` |
| Back from actions | `Back to {App display name} overview` |
| Turn off | `Turn off Skopeo in this tab` |

`{App display name}`, `{Entity noun}`, `{page noun}`, `{bounded entity label}`, and `{Specific action label}` come only from the validated profile/catalog projection. Missing tokens select a complete generic sentence; they are never shown as braces, blank text, raw hostname, slug, or inferred host copy.

### Action-label grammar

Ready action controls use a bounded specific verb plus app-native object: `Search messages`, `Open issue`, `List dashboards`, `Compare plans`, or `Create calendar event`. Generic `Submit`, `OK`, `Continue`, `Run`, `Execute`, `Save`, `Click here`, and bare `Cancel` are prohibited.

### Empty versus non-ready

The empty state appears only when the selected lens contains zero ready and zero relevant non-ready capabilities. If non-ready capabilities exist, show their honest status summary instead of claiming emptiness. No empty illustration, celebration, fabricated recommendation, or automatic learning action appears.

### Errors

Every error names the attempted action and one safe next step derived from a typed error. Unknown errors use: `{Specific action label} didn’t finish. Review the target and try the action again.` Never promise that retry will succeed. Never expose raw exception text, stack traces, secrets, selectors, request bodies, or host-page content.

## Consequence Gate

The gate appears only after the user selects one `t1-ready` write or destructive capability. Background authority is rechecked before the gate is staged and again before invocation.

### Required anatomy and copy

| Element | Write action | Destructive action |
|---------|--------------|--------------------|
| Eyebrow | `Changes data` | `Destructive action` |
| Title | `{Specific verb} {exact target noun}?` | `{Specific destructive verb} {exact target noun}?` |
| Body | `{Effect sentence} Target: {exact target}. {Material parameter summary}.` | `{Irreversible/recovery sentence} Target: {exact target}. {Material parameter summary}.` |
| Safe action | `Keep reviewing` | `Keep reviewing` |
| Confirm action | Repeat the exact specific action label | Repeat the exact destructive action label |
| Pending state | `{Specific action gerund}…` with controls unavailable | `{Specific action gerund}…` with controls unavailable |
| Stale state | `This confirmation expired because the page context changed. Review the action again.` | Same |

The effect, exact target, side-effect class, and every material parameter must fit as bounded text before confirmation. Secret values are represented by safe labels, never plaintext. If a target or material parameter cannot be represented safely and specifically, the gate does not open.

Use `role="alertdialog"` and `aria-modal="true"`. Initial focus goes to `Keep reviewing`. Source/Tab order is safe action, confirm action, turn-off action. The destructive gate uses the destructive keyline/text; the confirm control may use a restrained destructive fill only when contrast passes. A write gate uses orange only for its signal keyline and selected confirm action.

Closing, backing out, changing origin/context/profile/generation, or turning Skopeo off cancels the action token. Repeated activation produces exactly one invocation/audit attempt. The gate never calls a handler, recipe, fetch primitive, or host action directly; it delegates to the existing capability router after confirmation.

## Geometry, Placement, and Responsive Behavior

Phase 53.1 inherits the Phase 52 deterministic candidate order, collision rejection, pointer isolation, and exact geometry:

- full lens 240×40px; compact lens 88×40px;
- 16px viewport inset and 8px host-control clearance;
- preferred focused card width 320px and gate width 360px;
- card/gate `max-width: calc(100vw - 32px)` and `max-height: calc(100dvh - 32px)`;
- anchor mark 8×8px, chip minimum height 32px and maximum width 240px;
- one halo with a 2px outline and maximum 16px glow extent;
- rail 4px wide with 64px top/bottom reserve;
- visible compact controls 32×32px and action controls at least 40px high.

### Responsive states

| Viewport/condition | Contract |
|--------------------|----------|
| At least 480px CSS width | Use full lens when collision-safe; focused actions may remain in the 320px card |
| Below 480px CSS width | Use compact lens; focused/gate surfaces inset 16px on both sides; actions stack safe-first; compact tables become labelled fact lists |
| 200% browser zoom | Required controls and complete gate consequence remain reachable without Skopeo-caused horizontal page scroll |
| Unsafe collision | Try inherited corner candidates, then compact mode; if none is safe, show the side-panel unsafe-layout error and leave no page shell |
| Focused host control collision | Return to the prior attention level and announce that Skopeo cannot open without covering the current control |
| Semantic geometry invalidation | Withdraw dependent anchor/halo before resolving replacement; never interpolate between entities |

The shell does not reposition host nodes, reserve host layout space, cover scrollbars, or create a second side panel. Results scroll only inside the focused card. The rail remains status geometry, not a navigation scrollbar or decorative edge glow.

## Interaction and State Transitions

```text
OFF
  └─ explicit current-tab invoke → STARTING
       ├─ exact app + safe generic context → AMBIENT
       ├─ exact app + stable relevant entity → ANCHORED
       └─ uncertain/unsupported/unsafe → concise side-panel or lens state

AMBIENT / ANCHORED
  └─ Open {App} actions or entity chip → FOCUSED

FOCUSED
  ├─ select ready read → pending result → result / typed error
  └─ select ready write/destructive → INTERSTITIAL

INTERSTITIAL
  ├─ Keep reviewing / Escape → FOCUSED
  └─ exact confirm → one existing-router invocation → typed result / typed error

ANY ACTIVE
  └─ toggle off or Escape Escape → OFF with exact teardown
```

- Context/profile/genre resolution occurs only inside the current explicit Skopeo generation.
- App/profile/genre changes never preserve a selected capability, result, action token, or semantic identity across exact-origin boundaries.
- Same-origin SPA changes may preserve the shell only after a new context epoch commits. Dependent primitives withdraw before replacement.
- Lens changes are explicit Skopeo control activations. They may reorder capability groups but cannot change readiness or create semantic evidence.
- One Escape backs out one Skopeo attention level; inherited double-Escape within 600ms ends the complete current-tab generation.
- Starting, pending reads, and pending writes remain cancellable by turn-off. Late completion cannot repaint or announce after terminal state.
- No action fires on focus, hover, mount, page navigation, profile selection, or result rendering.

## Keyboard, Focus, and Accessibility

### Focus policy

- Ambient and Anchored do not move host-page focus on entry.
- Opening Focused records the actual Skopeo trigger and focuses the card title with `tabindex="-1"`.
- Focused source order is: visible back, lens/group controls, ready capability controls, result controls if any, turn-off.
- Non-ready status rows are not focusable unless they contain a specific trusted setup link.
- Opening Interstitial records its trigger, focuses `Keep reviewing`, and traps Tab only within the gate.
- Back/close restores focus with `focus({preventScroll: true})` when the recorded origin remains connected, visible, enabled, and authoritative. Otherwise use the preceding Skopeo back/trigger; never force focus to `body` or a guessed host node.
- Context withdrawal while Focused moves focus to the focused-card title, announces the withdrawal once, and removes entity-dependent actions.
- Focus outlines remain 2px orange with 2px offset and are never clipped.

### Roles and names

| Surface | Semantic contract |
|---------|-------------------|
| Ambient/Anchored container | `role="region"`; name `Skopeo for {App display name}` |
| Rail | Named status group; internal line/ticks decorative |
| Semantic mark | Pointer-transparent and decorative; relationship described by the entity chip/card |
| Entity chip | Native button; `Open actions for {entity noun} {entity label}` |
| Focused card | `role="region"`; name `{App display name} actions` or entity-specific title |
| Capability groups | Labelled groups with headings; readiness is text in each row |
| Ready capability | Native button with the exact specific action label |
| Result | Focused labelled region; announced once after completion, not per row |
| Consequence gate | `role="alertdialog"`, `aria-modal="true"`, labelled by exact consequence title, described by effect/target/parameters |
| Live region | The existing single atomic shell live region; no per-adapter/per-result live regions |

App-native vocabulary must remain intelligible without color, icon shape, position, or host context. Status labels are complete words. Counts and abbreviations have accessible expansions when their meaning is not universal.

### High contrast and forced colors

Use inherited forced-color mappings: Canvas/CanvasText for surfaces, ButtonFace/ButtonText for controls, and Highlight for focus/current marks. Ghosting becomes transparent. Risk, readiness, selection, and anomaly remain explicit in text.

## Host Integrity, Trust, and Failure States

1. The one host/envelope and all geometry-only layers remain pointer-transparent; only visible Skopeo controls accept pointer input.
2. Do not alter host `html`/`body`, overflow, classes, styles, focusability, `inert`, `aria-hidden`, selection, scroll, nodes, or event propagation.
3. Page content and descriptor/profile text are data, never instructions. Render bounded strings with `textContent` only.
4. Exact app identity comes from the admitted catalog/profile projection. A hostname substring, visible logo, page title, CSS class, label, or URL path cannot establish identity alone.
5. Stable entity identity comes only from allowlisted adapter evidence. Generic profiles remain unanchored.
6. Every render and invoke repeats generation, exact origin, profile version, context epoch, entity, and action-token authority immediately before side effects.
7. Uncertain, unsupported, stale, hostile, or unsafe input reduces attention and removes dependent actions; it never guesses a better-looking state.
8. Profile/catalog coverage does not imply live-host approval. Unsupported drift is shown honestly and recorded for UAT.
9. Turning off, replacement, hard navigation, or terminal error removes the sole host and returns all eleven owned resource categories to exact zero.

### Failure-state hierarchy

| Failure | Surface | Copy behavior | Page guarantee |
|---------|---------|---------------|----------------|
| Unsupported/restricted origin | Side-panel state; no page shell | Exact unsupported page guidance | No injection residue |
| Exact app known, context uncertain | Ambient lens only | `Skopeo can’t verify this view.` plus safe next step | No semantic mark or entity action |
| Profile/catalog inconsistency | Fail closed before page projection | Generic `Skopeo didn’t start safely.` and retry/update guidance in trusted extension UI | No partial/ad-hoc profile |
| Entity/geometry withdrawn | Ambient or app-level Focused | Target-withdrawn copy; entity actions removed | No wrong-target frame |
