# Phase 53.1 Code Review

**Reviewed:** 2026-07-18T01:14:44Z
**Depth:** standard
**Status:** issues_found

## Summary

The first fix iteration closes the original projection and injection failures: real generated Zillow and Notion rows now pass the authoritative projector and reach actual runtime configure, prepare, and commit, and the isolated content stack injects the projector before the resolver. Direct shell clicks, form submissions, and confirmation controls are also behind a closed ShadowRoot and trusted-event checks. The shared consequence bounds admit and render the tested minimum/maximum values, and an interstitial that cannot render is explicitly cancelled. The new structured-result adapter is bounded and selects only atoms authorized by the current profile renderer on its positive path.

Three release-blocking defects remain. A second capture-phase Escape handler bypasses the shell's trusted-event boundary. Both that handler and the shell's trusted Escape path back out of an interstitial without cancelling its background action token. Separately, the structured-result boundary still admits secret-shaped result data through an omitted key class and through the success-message field.

## Narrative Findings (AI reviewer)

### BL-01: The capture-phase runtime Escape handler bypasses the trusted-event boundary

**Classification:** BLOCKER — a host-page script can still drive HUD state and terminate the current generation
**Files:** `extension/content/skopeo-runtime.js:1380`, `extension/content/skopeo-runtime.js:1480-1508`, `extension/content/skopeo-shell.js:1229-1267`, `tests/skopeo-session-lifecycle.test.js:1528-1539`, `tests/skopeo-session-lifecycle.test.js:2183-2216`

**Issue:** The shell correctly rejects an Escape event unless `event.isTrusted === true`, but commit also installs `onKeydown` on `window` with capture enabled. That runtime handler has no trust check. For a real key event targeted inside the HUD, the runtime capture listener executes before the shell or collector listener; for a page-created event it still calls `shell.back()` or `requestKill('escape')`. A host script can therefore run `window.dispatchEvent(new KeyboardEvent('keydown', {key:'Escape'}))` to back the HUD or turn it off even though all direct shell controls reject synthetic input.

The integrated lifecycle test masks the defect: its fabricated event has no `isTrusted` property, yet the Ambient and double-Escape assertions still pass. They pass because the unguarded runtime listener, not the newly guarded shell boundary, consumes those events.

**Fix:** Remove the duplicate runtime Escape listener and let the shell own the keyboard boundary, or register only a trusted, bubble-phase fallback that runs after shell/form handlers and returns when they consumed the event. Add an integrated hostile-main-world regression that dispatches synthetic Escape at Ambient, Focused, a collector, and Interstitial and proves there is no attention change, outbound message, or teardown; retain real browser pointer/keyboard coverage for the legitimate path.

### BL-02: Escape/back dismisses a consequence gate without cancelling its action token

**Classification:** BLOCKER — a required cancellation path leaves live background authority behind
**Files:** `extension/content/skopeo-shell.js:1232-1265`, `extension/content/skopeo-shell.js:2323-2329`, `extension/content/skopeo-shell.js:2937-2949`, `extension/content/skopeo-runtime.js:851-861`, `extension/content/skopeo-runtime.js:1274-1278`, `extension/content/skopeo-runtime.js:1480-1508`

**Issue:** The visible `Keep reviewing` button explicitly emits `cancel-consequence` before calling `back()`. Escape does not. The shell's general Escape listener calls only `back()` and `onEscapeConsumed`; `back()` restores the suspended Focused scope without emitting an adaptive cancellation, and `onShellEscape` merely updates timestamps/attention. The runtime capture handler likewise calls `shell.back()` directly. Consequently `state.pendingConsequence` remains populated and no `skopeo:consequence-cancel` reaches the background gate after the user dismisses the alertdialog with Escape.

This violates the phase UI contract that closing or backing out cancels the action token and that `Keep reviewing / Escape` are equivalent. The token remains open until replacement, a later open, invalidation, or TTL expiry; runtime and visible attention also diverge in the interim. The maximum-boundary test cancels the gate manager directly, so it does not exercise this actual shell/runtime path.

**Fix:** Route every Interstitial exit through one generation-owned cancellation operation. A trusted Escape should consume the exact pending token through `finishConsequence('skopeo:consequence-cancel')`, clear pending state, and only then restore/recompose Focused; stale/failed cancellation must fail closed. Add an integrated real-projection write test that opens each boundary confirmation, presses trusted Escape, and requires exactly one cancel message with the exact token, zero router calls, no pending token, and a Focused shell. Cover the maximum accepted confirmation as well as the ordinary case.

### BL-03: The structured-result secret boundary has concrete bypasses

**Classification:** BLOCKER — remote/router result material can be rendered as plaintext secrets
**Files:** `extension/background.js:703-707`, `extension/background.js:763-817`, `extension/background.js:1148-1184`, `tests/skopeo-catalog-runtime.test.js:725-750`

**Issue:** `secretReadKey` omits the established broad `session` class and checks only `sessionid`. Thus data such as `{session: 'deadbeefdeadbeefdeadbeef'}` passes `closedReadData`, is converted to a fact/item, and reaches a non-generic renderer. The new success-message path is a second bypass: `typedReadResult` validates `routerResult.message` only with `boundedSkopeoText`, not `READ_SECRET_VALUE`/`safeReadText`. A successful result carrying `message: 'password=NEVER-CROSS'` therefore installs that plaintext in the completion notice even though the same value would be rejected inside `data`.

The regression covers only an `api_token` data key, so neither bypass is tested. Size/depth/node limits and renderer-genre selection do not mitigate the disclosure once these strings are admitted.

**Fix:** Reuse one canonical secret-name policy at this boundary, including `session`, authentication variants, and the project's existing secret-field classes. Pass success messages through the same secret-value and remote-address sanitizer as structured values (or replace any rejected message with the fixed completion copy); apply equivalent closed handling to error metadata before it crosses into content. Add production-controller negatives for `session`, `session_key`, auth variants, opaque credential values under those keys, and secret-bearing `message`, requiring only the generic fixed notice and proving the sent response contains none of the sentinel bytes.
