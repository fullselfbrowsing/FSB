# Roadmap: FSB v1.2.0 Skopeo

## Overview

Skopeo is built from the interaction boundary inward: first an explicitly invoked HUD that tears down cleanly, then a Drive/Docs proof of semantic anchoring, then a catalog-wide adaptive composer that gives every supported app a context-appropriate HUD from the shared design grammar. Only after that platform boundary is proven does FSB deepen the Drive vendor-contract pack through a permission-scoped source boundary, Chrome-local Graphify-style truth engine, governing-lineage and deadline logic, folder/reading projections, cited ask and policy gates, and current-user notification hardening. The milestone stays inside the Chrome extension, reuses existing FSB AI providers, and treats Drive/Docs contracts as the first deep capability pack rather than Skopeo's permanent product boundary.

## Milestone Boundaries

- The committed capability catalog is the minimum Skopeo coverage boundary: currently 2,314 descriptors across 128 app stems / 129 distinct services. Every service must resolve to an adaptive profile or an explicit fail-quiet disposition, and later catalog additions must enter the same coverage gate.
- The HUD is custom by composition, not by duplicated runtime: exact app identity, page genre, semantic entity, requested task, capability readiness, and action risk select app-native profiles, labels, anchors, renderers, primitives, and attention levels on top of one lifecycle and shell.
- Only verified executable capabilities may appear runnable. Guarded or pending states remain honest, and write/destructive actions preserve existing origin classification, denylist, consent, confirmation, serialization, and audit behavior.
- The Graphify-style engine is locally bundled JavaScript running inside the Chrome extension; upstream Graphify remains a selectively adapted design/code source, not a runtime dependency.
- Skopeo uses only the user's existing FSB AI provider path and bounded, permission-scoped excerpts. Existing MCP may optionally invoke or inspect Skopeo, but no new MCP server or daemon is required.
- No Python process, graph/vector database, GCP, NotebookLM, Google Sheets, required LM Studio setup, remote graph service, or separate contract application is introduced.
- v1.2 notifications target only the current FSB Chrome user when that user is the mapped owner. A missing or different owner is explicitly not locally deliverable.
- Phase 999.1 remains an existing side backlog outside v1.2.0; this roadmap does not change its status.

## Phase Details

### Phase 52: On-Demand HUD Lifecycle & Primitive Shell

**Goal**: Give users a safe, accessible Skopeo shell that appears only on request, uses one shared HUD grammar, and leaves the host page exactly as it found it when dismissed.

**Depends on**: v1.1.0 archive (Phase 51 complete)

**Requirements**: HUD-01, HUD-02, HUD-03, HUD-04, HUD-05, HUD-07, HUD-08

**Success Criteria** (what must be TRUE):

1. User can invoke Skopeo explicitly, while arbitrary pages never activate it automatically.
2. User can dismiss or kill Skopeo during active work; pending results are cancelled and cannot restore the HUD afterward.
3. After shutdown, the host has no remaining Skopeo visuals, layout changes, listeners, observers, focus hooks, or intercepted interaction.
4. Supported Drive and Docs controls remain usable without layout shift or unrelated event interception while the HUD is active.
5. The six shared primitives and attention levels work with keyboard, screen reader, visible focus, zoom, contrast, and reduced-motion behavior.

### Phase 54: Permission-Scoped Drive Corpus Boundary

**Goal**: Make current Drive identity and access the hard boundary for every enrolled source and every piece of derived intelligence.

**Depends on**: Phase 53.1

**Requirements**: CORPUS-01, CORPUS-02, CORPUS-03, CORPUS-04, CORPUS-05, CORPUS-06

**Success Criteria** (what must be TRUE):

1. User can enroll the designated `vendor agreements` folder by stable Drive identity and include only accessible vendor descendants.
2. Results are partitioned by active Drive account and enrolled corpus so another account or corpus cannot influence them.
3. Every expected source exposes an honest ready, pending, unreadable, download-blocked, inaccessible, or missing state, with access revalidated at each consequential use.
4. Deletion, revocation, or account switching removes all source-owned snippets, relationships, search hits, citations, counts, and alert evidence before subsequent display or query.
5. New, changed, moved, renamed, deleted, and revoked sources reconcile idempotently from stable identity and revision/content fingerprints without unnecessary full-document retention.

**Plans**: 8 plans

### Phase 55: Chrome-Local Graph & Incremental Truth Foundation

**Goal**: Implement the lightweight Graphify-style knowledge engine as trusted, locally bundled FSB JavaScript with source ownership, provenance, validation, and atomic incremental replacement.

**Depends on**: Phase 54

**Requirements**: LOCAL-01, LOCAL-02, LOCAL-03, LOCAL-04, LOCAL-05, LOCAL-06, LOCAL-07, TRUTH-01, TRUTH-05, TRUTH-10

**Success Criteria** (what must be TRUE):

1. User can build, update, query, and inspect contract intelligence entirely inside Chrome without installing Graphify, Python, a database, daemon, server, or separate application.
2. Bundled JavaScript constructs and traverses compact source-owned graph records and indexes in account/corpus-partitioned browser storage, surviving disposable MV3 runtimes.
3. Model-assisted work uses only the already configured FSB provider and only bounded, permission-scoped excerpts; no corpus-wide upload or additional AI setup is required.
4. Skopeo works without MCP, while existing FSB MCP may optionally invoke or inspect it without introducing a new server or tool-per-feature surface.
5. Closed schemas treat source and page content as untrusted data, and a validated source replacement atomically removes stale facts, relations, index entries, and alert consequences before recomputation; selectively reused upstream code is locally pinned and attributed.

### Phase 59: Current-User Alerts & Release Hardening

**Goal**: Notify the correct local Chrome user at the governing notice boundary and prove Skopeo's permission, truth, anchoring, and adversarial safety claims before release.

**Depends on**: Phase 58

**Requirements**: ALERT-01, ALERT-02, ALERT-03, ALERT-04, ALERT-05, VERIFY-01, VERIFY-02, VERIFY-03, VERIFY-04, VERIFY-05

**Success Criteria** (what must be TRUE):

1. When the current FSB Chrome user is the mapped owner, that user receives a local notification 90 days before the governing notice deadline with vendor, deadline, consequence, owner, and governing evidence; a different or absent owner is explicitly not locally deliverable.
2. Before delivery, Skopeo revalidates access, governing facts, deadline, recipient, and evidence revision, then records a deduplicated scheduled, attempted, delivered, failed, or missed state that reconciles after browser restart, wake, or delayed alarms.
3. Golden-corpus results match exact dates, addresses, governing paths, and calculations; ambiguous and permission-negative fixtures abstain without leaking source existence or derived information.
4. Repeated lifecycle and Drive virtualization/navigation tests show no wrong-target annotations or teardown residue, and source replacement, deletion, revocation, duplicate-alert, prompt-injection, malicious-filename, fake-citation, and cross-vendor-exfiltration negatives pass.
5. Live Drive UAT records representative Google Docs, text-bearing PDFs, blocked downloads, shared access, revocation, and account switching, with unsupported coverage reported rather than inferred.
