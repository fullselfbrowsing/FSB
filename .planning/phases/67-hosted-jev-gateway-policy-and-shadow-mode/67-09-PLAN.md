Router contract (this plan):
`createJevRouter({db, config, fetchImpl, now = Date.now, log = console, profiles = loadProfiles(), randomUUID = crypto.randomUUID, upstreamByteBudget = CONTRACT.BUDGETS.upstreamByteBudget})` returns an express.Router with:
- `router.post('/decide', configGate, bodyParser, handler)`; `router.all('*', ...)` -> 404 typed `invalid_request` body (so API paths never fall through to the showcase HTML); a router-local error middleware.
- Wire body, ok: `{ok:true, decisionId, instrumentVersion, servedModel, calibration:{status, profileId}, decisions, usage, cost, latencyMs}` (latencyMs = gateway latency). Fallback: `{ok:false, fallback, servedModel, httpStatus, latencyMs}` where httpStatus equals the HTTP status of this response. All responses set `Cache-Control: no-store`. `respond(res, status, body)` is the only code that writes to `res`: it returns false and does nothing when `res.headersSent` is true; otherwise it calls `res.set('Cache-Control', 'no-store')` and `res.status(status).json(body)` (the idiom of `showcase/server/src/routes/telemetry.js:217`) and returns true. `refuse(res, reason)` returns immediately when `res.headersSent` is true (no counter, no send); otherwise it calls `recordAggregateOnly` in try/catch and then `respond` with the typed fallback.
- Spend accounting (Pitfall 9): an in-memory `{dayUtc, usd}` accumulator seeded once per UTC day from `todaySpendUsd` (try/catch; on failure seed 0 and log the fixed line `[jev] spend seed failed`); for every request that reaches upstream add capUsd = the provider cost when it is greater than 0, else the estimate when it is greater than 0, else the request upper bound `bytes * config.inputUsdPerMtok / 1e6` (so every upstream attempt moves the accumulator by a positive amount, which bounds ledger rows per UTC day by dailyUsdCap divided by the smallest accrual); the same capUsd is passed to that attempt's `recordDecision(db, row, {capUsd})` on the ok path, on every upstream fallback and on the post-upstream server_error path alike, so jev_daily.cap_accrued_usd always matches the in-memory accrual and a same-day restart reseeds it from `todaySpendUsd`; refuse with spend_cap_reached when `usd >= config.dailyUsdCap` before acquiring the semaphore.
- Ledger policy (Pitfall 13, Pitfall 9, D-08): a per-decision row exists for every request that reached the upstream attempt and for no other request. The first statement after `semaphore.tryAcquire()` succeeds is `decisionId = randomUUID()` (returned to the client only inside an ok body). Immediately before `await callUpstream(...)` the handler sets `capUsd` to the request upper bound and `upstreamAttempted = true`. From then on exactly one `recordDecision(db, row, {capUsd})` call happens, through a single `writeLedger(row, capUsd)` helper that sets `ledgerWritten = true` before calling it: the row outcome is 'ok' or an upstream-stage reason on the normal path, or 'server_error' when the outer catch fires with `upstreamAttempted` true and `ledgerWritten` false. A post-upstream server_error row carries the upstream result's servedModel, upstreamStatus and upstreamLatencyMs (null when callUpstream never returned), usage and cost from an ok upstream result (otherwise null with source 'unavailable'), calibrationStatus null, instrumentVersion INSTRUMENT_VERSION, and the validated request's kinds, elementCount and requestBytes; its capUsd is the refined accrual when callUpstream returned, else the byte upper bound, and the outer catch first adds that capUsd to the in-memory accumulator when the normal path had not accrued it yet (`accrued` flag), so memory and jev_daily agree. When the outer catch fires with `ledgerWritten` already true (a fault after the attempt's row and log line were written, for example while sending the response), it writes nothing more: no second row, no `recordAggregateOnly` call, no second log line, and at most one 500 through `respond` when the headers have not gone out yet. Every other outcome (disabled, not_configured, body-parser rejections, the 404 catch-all, invalid_request, sensitive_goal, payload_too_large from the budget, spend_cap_reached, busy, server_error from the error middleware, and server_error from the outer catch before any upstream attempt, such as a throwing randomUUID) calls only `recordAggregateOnly(db, {dayUtc, outcome})`, which touches one bounded jev_daily row per (day, outcome); nothing was spent on those paths. No ledger row is ever built from a body that failed validation, so `kinds`, `elementCount` and `requestBytes` always come from a validated request. Both calls sit inside try/catch with the fixed log line `[jev] ledger write failed`.
- One log line per ledger row (the post-upstream server_error row included), written inside `writeLedger` only after recordDecision is attempted: `log.log(formatDecisionLog(row))`. The line is the prefix `[jev] decision ` followed by a JSON payload whose first field is decisionId (67-05 `formatDecisionLog`), so the operator can find the matching row with `node src/jev/report.js --recent N` (67-05). Aggregate-only outcomes write no per-request log line.
