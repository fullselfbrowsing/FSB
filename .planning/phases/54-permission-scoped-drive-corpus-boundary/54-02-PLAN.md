<interfaces>
The migration uses named messages only. All direct local persistence is owned by `background.js` or a new `trusted-local-feature-store.js` that is never injected. Dual-loaded utilities are validation/redaction/message clients only. Final message names may follow the repository prefix convention, but the closed operations are:
```text
diagnostic append (bounded/redacted record only)
automation log append/load
automation session save/load/list/delete/clear
automation DOM snapshot load
element-cache configuration get/change notification
solveCaptcha({ captchaType, sitekey })
```
There is no message accepting arbitrary `key`, `keys`, `value`, `operation`, `storageArea`, or unrestricted record namespaces. `solveCaptcha` accepts neither `apiKey` nor `pageUrl`; background reads settings and derives URL/tab from `sender.tab`.
</interfaces>

<threat_model>
## Trust boundaries

| Boundary | Risk |
|---|---|
| Injected/content and dual-loaded utilities → extension local storage | Page-compromised code can select a content branch or load a shared helper to read corpus metadata, account identity, API keys, or write trusted records. |
| Feature-specific runtime messages → background | A generic bridge or forged tab/URL can become a storage or secret oracle. |
| Remote/host strings → diagnostics and automation logs | Raw errors, page text, credentials, or oversized data can persist indefinitely. |
| Worker boot → first trusted-local operation | Corpus storage can open before the area restriction is installed. |

## STRIDE register

| Threat ID | Severity | Category | Disposition | Mitigation and automated negative proof |
|---|---:|---|---|---|
| T-54-08 | High | Elevation of privilege / Information disclosure | mitigate | Call `setAccessLevel({accessLevel:'TRUSTED_CONTEXTS'})` before corpus/store boot; move persistence wholly into background/the background-only trusted store; require zero direct-local calls/listeners in every dual-loaded/injected file branch; and statically enumerate both injected lists plus dependency closure. Fake-Chrome and static tests reject every remaining path. |
| T-54-01 | High | Spoofing | mitigate | Every fixed message validates `sender.tab.id`, current URL where relevant, exact field set/type/size, and feature ownership; content-supplied tab/URL/account fields are ignored or rejected. Negative tests forge each. |
| T-54-07 | High | Information disclosure / Repudiation | mitigate | Redaction and caps run in background before persistence; raw errors, credentials, IDs, HTML, and full page/source text are rejected. Tests inject secrets and hostile strings, then inspect storage/log output. |
| T-54-06 | High | Tampering | mitigate | Access-level setup failure is terminal for corpus startup and cannot silently fall back to content-readable storage. Tests reject/omit the API and prove no corpus boot callback occurs. |
| T-54-09 | Medium | Denial of service | mitigate | Each message has exact record/count/byte/rate caps and closed error responses; oversized batches and floods are rejected without mutation. |
</threat_model>
