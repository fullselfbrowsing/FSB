### MCP tool surface (mcp/ footprint)
- **D-02:** One tool, registered with `server.tool()` in a new `mcp/src/tools/settings.ts` (`registerSettingsTool`) and wired from `mcp/src/runtime.ts`, so stdio and HTTP sessions both get it. It is never added to `TOOL_REGISTRY` (`extension/ai/tool-definitions.js`), which keeps `EXPECTED_NON_TRIGGER_REGISTRY_HASH` (`tests/capability-mcp-surface.test.js:58`) and the autopilot tool list unchanged. The precedent is the vault and capability tools. None of the six force-tracked `mcp/build` files change. The MCP package version does not change here; Phase 71 does the planned minor bump (REL-02).
- **D-03:** The tool is named `settings`. Its description is one or two sentences in the deduplicated style Phase 69 will adopt: no `tab_id`, visual-session, change_report or multi-agent boilerplate, and roughly 200 characters or less. Parameter descriptions are one short clause each. Do not use the leftover name `get_extension_config` (`mcp/src/queue.ts:47`, a read-only queue entry with no tool); leave that stale entry alone. Add no annotations; the baseline has none.
- **D-04:** Input is two optional parameters:
  - `key`: string, free-form. Never an enum of keys, so a new schema key needs no `mcp/src` edit (SC4).
  - `value`: JSON Schema exactly `{"type":"string"}`. JSON booleans and finite numbers are accepted and turned into strings before validation; `null`, objects and arrays are rejected. Use `z.preprocess(..., z.string())` or an equivalent. A local probe showed this emits `type: string`. Do not use `z.union`, `z.any`, `anyOf` or a type array (see External Research in the discussion log).

  Modes:
  - no arguments: read every setting
  - `key` only: read that one setting with its constraints (type, allowed values or range, writable or not)
  - `key` and `value`: write that one setting
  - `value` without `key`: typed request error

  The extension parses `value` by the key's schema type:
  - booleans: `true`/`false`
  - integers: base-10 digits only
  - enums: exact match
  - strings: trimmed and length-bounded
- **D-05:** Reads and writes both skip the TaskQueue. The tool calls the bridge directly, as `stop_task` does (`mcp/src/tools/autopilot.ts` ~215-233), and is not added to `queue.ts` `readOnlyTools`, since writes are not read-only. It uses `sendAgentScopedBridgeMessage` (`mcp/src/agent-bridge.ts`), so the extension receives `agentId`. That gives it the client label for logs and the journal, session-recording correlation, and delegated-run detection (D-20). Short bridge timeouts (about 10 s).
- **D-06:** Two new bridge message types, `mcp:get-settings` and `mcp:set-setting`:
  - appended at the end of `MCPMessageType` (`mcp/src/types.ts:8-56`) and to `mergedAdditiveMessageTypes` in `tests/mcp-version-parity.test.js` (~364-370); the pre-Phase-57 list and order do not change (INV-01)
  - `mcp:get-settings` joins `MCP_ICON_READ_MESSAGE_TYPES` (`extension/ws/mcp-bridge-client.js:69-78`)
  - both are reachable only through the MCP bridge, as dispatcher message routes in `MCP_PHASE199_MESSAGE_ROUTES` (`extension/ws/mcp-tool-dispatcher.js:103-131`), or as a bridge-client case if the planner finds that cleaner within D-19
  - neither is ever handled by `chrome.runtime.onMessage`, so content scripts and pages cannot reach them
- **D-07:** Output and errors:
  - On success the tool formats its own compact single-line JSON (`JSON.stringify(x)`, no indentation). It does not use `mapFSBError`'s pretty-printed success path (`mcp/src/errors.ts` ~452).
  - Read-all returns `{"settings":{...},"readOnly":[...]}`. `readOnly` lists the secret and endpoint keys.
  - Single-key read returns `{"key","value","type","writable"}` plus `range` or `values` where applicable.
  - Write returns `{"key","value","previous","changed":[...]}`, where `changed` lists every key written (normally one; two for a `modelProvider` change, D-15).
  - Failures use typed codes that pass through `errors.ts` verbatim. Extend the passthrough regex (~152) or `CODE_ONLY_ERROR_KEYS` (~60) with a `SETTING_` family, so a message that mentions `modelName` cannot collapse into `configuration_error` and "not found" cannot become `element_not_found` (~159-170). Codes cover at least:
    - unknown key
    - protected key (secret or endpoint)
    - invalid value, with the allowed range or values in the error
    - malformed request
    - provider not ready
    - delegated-run write refused
  - No error text, raw error or stderr line (`errors.ts` ~478-485) ever contains the submitted `value`.

### Settings inventory and classification
- **D-08:** One declarative settings schema is the single source of truth for MCP reads and writes. Each entry has: key, type, effective default, bounds or enum, class (`writable`, `secret` or `endpoint`), and group (for the provider rules in D-15).
  - It lives in `extension/config/config.js`, a classic script already loaded by the service worker (`extension/background.js:8`) and the control panel (`extension/ui/control_panel.html:1965`). That adds no `importScripts` and moves neither pin in `tests/lattice-provider-bridge-smoke.test.js` (count 334). Tests only `require()` `config.js` and check behaviour.
  - The existing `Config.defaults`, `init-config.js` defaults and `options.js` `defaultSettings` values are not changed in this phase, because changing them would change behaviour.
  - Phase 68 adds the Jev key as one new entry here.
- **D-09:** "Every control-panel setting" means every key the control panel writes to `chrome.storage.local`:
  - `saveSettings`'s object (`extension/ui/options.js:2329-2378`): `providerKind`, `agentProviderId`, `modelProvider`, `modelName`, the six API keys, `customEndpoint`, `lmstudioBaseUrl`, `maxIterations`, `debugMode`, `domOptimization`, `maxDOMElements`, `elementCacheSize`, `prioritizeViewport`, `animatedActionHighlights`, `showSidepanelProgress`, `enableLogin`, `captchaSolverEnabled`, `captchaApiKey`, `sttProvider`, `voiceInputEnabled`, `autoRefineSiteMaps`, `fsbAgentCap`, `fsbTriggerCap`, `fsbChangeReportsEnabled`, `fsbMcpSessionRecordingEnabled`, `fsbMcpSessionRetentionDays`
  - `autoAnalyzeMemories` (`options.js:7326-7334`)
  - `fsbTelemetryOptOut` (`extension/ui/install-identity-ui.js:53-71`)
  - the Sync keys `serverUrl` and `serverHashKey` (`options.js:7012-7045`)

  Excluded:
  - the theme: page `localStorage`, `options.js:2745`, unreachable from the service worker
  - legacy `speedMode`
  - `enableSavedPayments`: a checkbox at `control_panel.html:1660` that no script reads or writes
  - `serverSyncEnabled`: no control-panel writer
  - the consent and audit stores
  - delegation trust (Phase 61 keeps it challenge-bound; `tests/delegation-phase-contract.test.js:2730-2752`)
  - vault credential and payment records
  - every other internal key

  The schema is an explicit allowlist, so all of these are excluded by construction. Everything in the inventory that is not a secret or endpoint is writable, including telemetry, session recording and safety-adjacent toggles. The owner rejected a narrower allowlist (66-DISCUSSION-LOG "Added by the user").
- **D-10:** Secrets: `apiKey`, `geminiApiKey`, `openaiApiKey`, `anthropicApiKey`, `openrouterApiKey`, `customApiKey`, `captchaApiKey`, `serverHashKey`.
  - On read each shows the fixed marker `"[set]"` when non-empty and `""` when empty. Never a prefix, suffix, length or hash.
  - Every write is refused with the protected-key code, before the value is parsed or stored.
  - Do not reuse `extension/config/secure-config.js` `sensitiveKeys`: it omits `openrouterApiKey` and `serverHashKey`.
- **D-11 (auto-resolved ROADMAP open question a):** The endpoint settings `customEndpoint`, `lmstudioBaseUrl` and `serverUrl` count as secrets for writing. Writes are refused with the same protected-key code.
  - Why: each endpoint receives a stored secret or page data.
    - `customApiKey` is sent to `customEndpoint` (`config.js` `getApiKey`).
    - A `serverUrl` change makes the relay reconnect and present `serverHashKey` to the new host (`background.js` ~21447-21470).
    - `lmstudioBaseUrl` receives prompts and page context.
    - `serverUrl` is not even user-editable in the panel (hidden input, `control_panel.html:894`).
  - On read they show origin only: `scheme://host[:port]`, plus `"/..."` when a path, query or fragment existed. A value that cannot be parsed shows `"[set]"`, and an empty value shows `""`. This keeps diagnostics such as "which LM Studio host?" without leaking path tokens, userinfo or query keys.
- **D-12:** A read returns the stored value. When nothing is stored, it returns the effective default the consuming code actually uses. A read never writes. Known places where the default copies disagree:
  - `showSidepanelProgress` is `true` in effect (`sidepanel.js:3709,4100` use `?? true`; `options.js:26`), but `false` in `config.js:46` and `init-config.js`.
  - `serverUrl` is `https://full-selfbrowsing.com` in effect (`ws-client.js:7`, `options.js:7012`), but `fly.dev` in `config.js` and `init-config.js`.
  - `fsbAgentCap` is the computed recommendation (`FsbAgentCapRecommendation`, loaded at `background.js:36`).
  - `autoAnalyzeMemories` defaults to `true`.

  A parity test pins these and fails on any new drift between the schema's effective defaults and the three default copies (`config.js`, `init-config.js`, `options.js`).

### Write path: validation, storage, propagation
- **D-13:** A write runs in the service worker and calls `chrome.storage.local.set` with only the changed key(s). Nothing else is added to notify consumers; they already react to storage:
  - the `Config` cache clears on any local change (`config.js:67-75`)
  - `run_task` reads storage at every start (`fsbReadAuthoritativeProviderConfig`, `background.js:1730-1743`)
  - `debugMode`, `fsbTriggerCap` and the Sync keys are handled at `background.js` ~21424-21470
  - the agent cap is re-clamped by `agent-registry.js`
  - change reports are watched by `mcp-tool-dispatcher.js` ~12-30
  - recording by `mcp-session-recorder.js`
  - the side panel listens for `showSidepanelProgress`

  An MCP write changes stored values only. UI-only side effects do not run: no microphone-permission tab for `voiceInputEnabled`, no discovery or connection test, no toasts. Writing a value equal to the stored one succeeds with `changed: []` and does no storage write.
- **D-14:** Validation is strict.
  - A wrong type, out-of-range number or unknown enum value returns the invalid-value code with the allowed range or values, and nothing is written. That holds even where the panel would quietly clamp.
  - Bounds come from the schema: `maxIterations` 50-500, `maxDOMElements` 500-5000, `elementCacheSize` 10-1000, `fsbAgentCap` and `fsbTriggerCap` 1-64, `fsbMcpSessionRetentionDays` 1-365. Enums such as `sttProvider` `browser|whisper` are also schema entries.
  - The panel keeps its own clamping (`options.js:60-80`, ~2366-2372). A parity test proves the panel and the schema agree: `control_panel.html` `data-min`/`data-max` (467, 494, 515, 542, 584, 661) and the clamp helpers must equal the schema bounds.
- **D-15:** The provider keys are writable under group rules. Each call still names one key.
  - **`modelProvider`:** the closed seven ids (`xai`, `gemini`, `openai`, `anthropic`, `openrouter`, `lmstudio`, `custom`; INV-03).
    - A change also sets `modelName` to that provider's default from `config.js` `validateAndCorrectModel`'s `defaultModels`. That default is `""` for `lmstudio` and `custom`; `fsbResolveLmStudioModelForStart` (`background.js:1744-1787`) resolves LM Studio at start.
    - The response lists both keys in `changed`.
    - A hosted provider (`xai`, `gemini`, `openai`, `anthropic`, `openrouter`) is refused with the provider-not-ready code unless its API key is already stored. `custom` is refused unless `customEndpoint` is set.
  - **`modelName`:**
    - Hosted providers: the id must be in the built-in list (`config.js` `availableModels`) or the discovery cache (`getDiscoveredModelIds`, `extension/ai/model-discovery.js:332`). No network call. The error lists the known ids, capped, and suggests refreshing models in Settings.
    - `lmstudio` and `custom`: any bounded string.
  - **`providerKind`:** `api|agent`. `agent` requires a non-empty shipped `agentProviderId` (`FsbDelegationProviders.isShippedId`, `extension/utils/delegation-providers.js:174`).
  - **`agentProviderId`:** a shipped id or `""`.
  - None of these writes touches delegation trust. A delegated start still needs the challenge-bound consent.
- **D-16:** An open control panel follows MCP writes.
  - The panel tracks which fields the user has touched since the last load or save.
  - A `storage.onChanged` listener for schema keys updates untouched fields in place, together with their persisted baselines (`persistedProviderSelection`, `persistedVoiceInputEnabled`).
  - It does this without rerunning `loadSettings()` or provider discovery.
  - Fields the user is editing are left alone; their pending edit wins on Save, which is the user's explicit choice.
  - Without this, `saveSettings` (which writes every field, `options.js:2380`) would silently revert MCP writes.
  - Automated proof uses a DOM-stub test. The visual check goes to V5.
- **D-17:** The Phase 68 Jev switch will be a boolean schema entry, default off, plus an Advanced Settings control, stored under one `chrome.storage.local` key. The tool needs no change for it. This phase proves that with a test-only fixture entry that is readable and writable through the route with zero `mcp/src` edits.

### Operator logging and recording hygiene
- **D-18 (auto-resolved ROADMAP open question b):** Yes, settings changed over MCP are logged for the operator.
  - Each accepted write records: key, previous and new value (never secret by construction, D-10/D-11), the MCP client label (`resolveMcpClientLabel`) and the time.
  - Each refused write records: the key (only if it matches `^[A-Za-z][A-Za-z0-9_]{0,63}$`, else `"[invalid]"`) and the error code. Never the value.
  - Both go into the MCP session journal through the normal route recording, and into a separate `automationLogger` line that is written even when `fsbMcpSessionRecordingEnabled` is off. A client could turn recording off first; `automationLogs` persists and `get_logs` can read it.
  - Reads are journaled through normal recording only.
  - No new UI.
- **D-19:** The new routes get their own recording sanitizer.
  - The request `value` is never persisted. The journal request keeps `key` only, and the accepted new value is taken from the response.
  - Read responses are recorded as a summary (key count), not the full map.
  - Add this next to `sanitizeMcpMessageResponseForRecording` (`mcp-tool-dispatcher.js:913`). The recorder's key-name redaction (`SENSITIVE_KEY_PATTERN`, `mcp-session-recorder.js:141`) would miss `{key:'apiKey', value:'sk-...'}`, and it misses `serverHashKey` entirely.
  - Tests prove that a refused secret write leaves no trace of the value in storage, the journal, `automationLogs`, the MCP error text or stderr.

## Summary

Every integration point CONTEXT names exists as described. Code-level verification also found **six places where the locked design needs a concrete mechanism the CONTEXT text does not spell out**. Each would cause a silent failure if missed:

1. **Routing needs two edits, not one.** `MCPBridgeClient._routeMessage` is an explicit `switch` whose `default` throws `Unknown MCP message type`, and there is no generic `hasMcpMessageRoute` fallback. A dispatcher route entry alone is unreachable. Each new type needs a dispatcher entry AND a `case` that calls `dispatchMcpMessageRoute`.
2. **A `SETTING_` passthrough alone gives the wrong error text.** The code reaches `buildLayeredDetail`'s `default` arm, which prints `Detected: Page navigation … Next action: Refresh page state with read_page or get_dom_snapshot`. `errors.ts` needs a small `SETTING_` branch with its own layer label.
3. **The session recorder stores `requestPayload: payload` unredacted.** Its pattern redaction misses a top-level `value`. Also, the v2 journal keeps only `JOURNAL_ACTION_RESULT_FIELDS` for non-read routes, which would drop `key`, `value` and `previous`. The sanitizer must therefore act inside the existing `sessionRecordEntry`, which five source pins guard, and both new types must join `JOURNAL_FULL_RESULT_TOOLS`.
4. **The SW model-discovery map goes stale.** It hydrates from storage only once, and the control panel runs its own discovery and writes `fsbDiscoveryCache`. D-15's cache check should read `fsbDiscoveryCache` from storage directly.
5. **Version skew can journal a secret.** An older extension sends `mcp:set-setting` to its `default` arm, which journals the raw payload, `value` included. A pre-write single-key read stops the value leaving the MCP process unless the key is known-writable on a supporting extension.
6. **D-16 cannot be met by display refresh alone.** Re-rendering the provider group requires live discovery, which the panel runs with `bypassCache` (network). The actual guarantee must be a Save-time exclusion of keys that changed externally and that the user has not touched.

The MCP side is small and verified. With SDK 1.29.0 and zod 3.25.76, `z.preprocess(v => boolean|finite number ? String(v) : v, z.string())` emits exactly `{"type":"string"}`. It converts `true`, `50` and `1.5`, and rejects `null`, objects and arrays with zod errors that name the type but never echo the value (probed through a real in-memory MCP client on Node 24 and Node 20). The 72-tool baseline digest, computed with the bench's own `toolsListDigest` (`scripts/bench/lib/identity.mjs`), is `{count:72, sha256:"8321cc7234a7e1d817b5a3e818e75e243d76e60d1911d88b410d38147c8c4a05"}`. That is the value the D-21 contract test pins and the value V1 records at `8a058bdf`.

**Primary recommendation:** Build in four waves.
1. A pure schema module (IIFE in `config.js`, one global) with three parity tests.
2. Dispatcher routes, bridge cases, the write lock, the delegated-write gate, recording sanitizers and log lines, all proven with a fake `chrome.storage`.
3. `settings.ts`, `types.ts`, `errors.ts` and `runtime.ts`, proven end to end by wiring the built MCP tool to the real dispatcher through a fake bridge (no ports).
4. Panel sync through a small `FSBSettingsSync` hook in `options.js`, proven with the existing `require('options.js')` shim pattern.

### Pattern 1: The tool (queue-free, agent-scoped, compact output)
**What:** A `stop_task`-style direct bridge call with a host-safe string schema.
**When to use:** The only tool this phase adds.
```typescript
// Source: verified against mcp/src/tools/autopilot.ts (stop_task) + local zod probe
const SETTINGS_TIMEOUT_MS = 10_000;
const toWireString = (v: unknown) =>
  typeof v === 'boolean' || (typeof v === 'number' && Number.isFinite(v)) ? String(v) : v;

server.tool(
  'settings',
  'Read or change FSB settings. No args returns all; key returns one with its allowed values; key and value sets it. API keys and endpoints are read-only.',
  {
    key: z.string().optional().describe('Setting name'),
    value: z.preprocess(toWireString, z.string()).optional()
      .describe('New value (string; true/false and numbers accepted)'),
  },
  async ({ key, value }) => {
    if (!bridge.isConnected) return mapFSBError({ success: false, error: 'extension_not_connected' });
    // ... see Pattern 5 for the write flow; NEVER console.error(args)
```

### Pattern 4: Recording sanitizer placed inside the existing entry
```javascript
// mcp-tool-dispatcher.js, inside the existing `var sessionRecordEntry = {` (do NOT add a second recordDispatch call)
requestPayload: sanitizeMcpMessageRequestForRecording(type, payload),   // was: requestPayload: payload,
response: sanitizeMcpMessageResponseForRecording(type, response),       // extend with a settings branch

function sanitizeMcpMessageRequestForRecording(type, payload) {
  if (type !== 'mcp:set-setting' && type !== 'mcp:get-settings') return payload;   // byte-identical for others
  if (!payload || typeof payload !== 'object') return payload;
  var copy = Object.assign({}, payload);   // keeps agentId/recordingRunId/recordingCallId (recordDispatch needs agentId)
  delete copy.value;
  if (typeof copy.key === 'string' && !/^[A-Za-z][A-Za-z0-9_]{0,63}$/.test(copy.key)) copy.key = '[invalid]';
  return copy;
}
```
The response branch records: read-all → `{ success, keyCount }`; single read → `{ success, key, writable }`; write → `{ success, key, value, previous, changed }`, which is safe because only writable keys succeed; failure → `{ success:false, code, key }`. Add `'mcp:get-settings': 1, 'mcp:set-setting': 1` to `JOURNAL_FULL_RESULT_TOOLS` in `mcp-session-recorder.js`. Otherwise `_compactJournalActionResult` keeps only `success`, `changed` and `code` from the write, and D-18's journal half silently loses `key`, `previous` and `value`.

### Pattern 5: Write flow with a value-safe preflight (recommended)
1. MCP side: `value !== undefined && key === undefined` → return `SETTING_REQUEST_INVALID` locally.
2. MCP side: send `mcp:get-settings {key}`.
   - If it fails with `/^Unknown MCP message type: mcp:get-settings$/` → return `SETTING_UNSUPPORTED` ("update the FSB extension"); the value never left the process.
   - If `writable !== true` (unknown, secret or endpoint) → send `mcp:set-setting {key}` **without** `value`. The extension refuses on class or unknown key before looking at `value`, logs the refusal (D-18), and returns the code.
   - Otherwise → send `mcp:set-setting {key, value}`.
3. The extension remains authoritative and independently refuses secret/endpoint writes even when a raw `{key:'apiKey', value:'sk-…'}` arrives (defence in depth; tested directly).

**Why:** An older extension's `default` arm calls `_recordUnsupportedMcpMessage(type, payload)`, which passes the raw payload to `recordDispatch`. The recorder's `_sanitizeRequestPayload(payload)` calls `_sanitizeReplayValue(payload, {}, false)`, and a top-level `value` is only redacted when `sensitiveTarget` is true, which a sibling `key` never triggers (`SENSITIVE_TARGET_METADATA_KEY_PATTERN` = `selector|field|name|input|target|…`). The value would be persisted in plain text in that build's journal `[VERIFIED: mcp-session-recorder.js:141-150, 435-452, 657-663; mcp-bridge-client.js:1587, 1928-1956]`. Cost: one extra local round trip per write.

### Pattern 7: Open control panel sync (D-16)
**Correctness guarantee:** a Save-time filter. **Cosmetic layer:** an in-place refresh.
- Expose `globalThis.FSBSettingsSync` at load time, the same way `FSBDiscoveryUI` is exposed (`tests/model-discovery-ui.test.js` requires `options.js` under minimal shims and reads the hook). Pure helpers:
  - `noteTouched(key)`
  - `noteSelfWrite(obj)`
  - `noteStorageChanges(changes, area)` → returns `{ apply: {key: value}, pending: Set }`
  - `filterForSave(settingsObj)` → deletes keys changed externally and untouched by the user
  - `reset()` on load and after a successful save
- **Touched tracking:** map each form control to its key. Coupled controls collapse to one key: the slider and number input for `maxIterations`/`maxDOMElements`, the preset and custom inputs for `elementCacheSize`, the agent-cap input and reset button. Any provider control (kind radio, `modelProvider` select, model select) marks all four provider-group keys as touched.
- **Self-write echo:** the panel's own `chrome.storage.local.set(settings)` (and the LM Studio migration at `loadSettings`) fires the panel's own `onChanged`. Record what the panel just wrote and ignore matching `newValue`s, or every Save looks like an external change.
- **In-place refresh** for untouched simple keys reuses the exact statements `loadSettings` already uses: slider, input and display; stepper `refreshStepper`; `setAgentCapControlValue`; visibility helpers for `enableLogin`/`captchaSolverEnabled`; and update `persistedVoiceInputEnabled` together with the `voiceInputEnabled` checkbox, or Save's `handleSavedChange(prev, next)` opens the microphone-permission tab.
- **Provider group:** do NOT call `setProviderSelection`. It runs `runApiProviderSelectionPath` → `FSBDiscoveryUI.runDiscovery`, which the panel runs with `bypassCache` (network). Leave the visible provider controls alone and rely on `filterForSave`. Also leave `persistedProviderSelection` matching the visible form while provider keys are pending. If it were updated alone, `validateHostedApiSettingsSelection` would see form ≠ persisted and refuse the Save (toast), discarding unrelated edits.
- Keep the pinned text in `saveSettings`: `chrome.storage.local.set(settings` after the LM guard, and the exact `modelName: selectedModelName || persistedProviderSelection.modelName || 'grok-4-1-fast'` line (`tests/lmstudio-settings-persistence.test.js`). Call `filterForSave(settings)` immediately before `chrome.storage.local.set(settings, …)`. After the save callback, rebuild `persistedProviderSelection` only from keys actually written.

### Anti-Patterns to Avoid
- **Listing schema keys in `mcp/src`:** breaks SC4. Add a test asserting no production schema key string appears in `mcp/src/tools/settings.ts`.
- **A second `fsbMcpSessionRecorder.recordDispatch(` call for settings:** breaks `tests/mcp-session-recorder.test.js:887-911` (exactly one redacted ingress, inside the single `_mcpMetricsSuppressInner` gate).
- **Throwing from the handler:** the thrown message goes to `mcp:error`, then the bridge stderr log (`error="…"`) and `mapFSBError`'s `raw=` stderr line.
- **Logging tool args MCP-side:** only `manual.ts:176` logs params today; the settings tool must not.
- **Writing defaults on read:** reads never write (D-12). Note `Config.loadFromStorage` already self-corrects `modelName` on load; do not route reads through it.
- **Reusing `secure-config.js` `sensitiveKeys`:** it omits `openrouterApiKey` and `serverHashKey` (D-10).

## Common Pitfalls

### Pitfall 1: Dispatcher route without a bridge-client case
**What goes wrong:** `mcp:get-settings` returns `Unknown MCP message type: mcp:get-settings` and gets journaled as an unsupported message.
**Why it happens:** `_routeMessage` is a closed `switch`; `default` calls `_recordUnsupportedMcpMessage` and throws. There is no `hasMcpMessageRoute` fallback `[VERIFIED: mcp-bridge-client.js:1406-1589]`.
**How to avoid:** add both (Pattern 2). The route test calls `client._routeMessage` on the vm-loaded bridge client (the `tests/mcp-bridge-background-dispatch.test.js` harness pattern).
**Warning signs:** the routing-contract test passes (`hasMcpMessageRoute` true) while the e2e test gets an unknown-type error.

### Pitfall 2: The `SETTING_` passthrough renders as "Page navigation"
**What goes wrong:** `Detected: Page navigation / Why: <msg> / Next action: Refresh page state with read_page or get_dom_snapshot`.
**Why it happens:** passthrough codes fall into `buildLayeredDetail`'s `default` arm `[VERIFIED: errors.ts:408-418]`.
**How to avoid:** add `SETTING_.+` to the passthrough regex (`errors.ts:152`) and, before the `switch`, `if (errorKey.startsWith('SETTING_')) return { detected: LAYER_LABELS.settings, why: \`${errorKey}: ${errorMsg}\`, nextAction: recoveryHint || 'Call settings with key only to see allowed values.' }` with a new `LAYER_LABELS.settings = 'Settings'`. Set `code`, `errorCode` and `error` on the extension result; keep `error` value-free. Other codes' text is unchanged (the existing tests are behavioural: `capability-router`, `capability-interpreter`).
**Warning signs:** a settings error mentioning `modelName` renders as "Configuration"; "not found" renders as "element_not_found".

### Pitfall 3: Raw `requestPayload` in the session journal
**What goes wrong:** `{key:'apiKey', value:'sk-…'}` persists in `fsbMcpSessionBuffer`/journal.
**Why it happens:** `sessionRecordEntry.requestPayload = payload` (`mcp-tool-dispatcher.js:860`), and the recorder only redacts by key-name pattern or sensitive target.
**How to avoid:** Pattern 4, plus a sentinel-value test that greps everything captured.

### Pitfall 4: The journal drops the write's `key`, `previous` and `value`
**What goes wrong:** D-18's journal entry shows only `{success, changed}`.
**Why it happens:** non-read routes use `_compactJournalActionResult`, which keeps only `JOURNAL_ACTION_RESULT_FIELDS` `[VERIFIED: mcp-session-recorder.js:107-131, 912-935]`.
**How to avoid:** add both types to `JOURNAL_FULL_RESULT_TOOLS`. Safe, because the dispatcher sanitizer has already reduced the response. Tested with the `journalStub` pattern in `tests/mcp-session-recorder-journal.test.js` (behavioural, not a pinned set).

### Pitfall 5: A replay re-executes a settings write
**What goes wrong:** `replay_session` dispatches any routed `mcp:*` step through `dispatchMcpMessageRoute` (`background.js:8658-8660`).
**Why it is safe today:** `classifyReplayEntry` returns `inspect-only/unsupported` for `mcp:set-setting` (it is in no replay set and not in `TOOL_REGISTRY`), and D-19 never persists `value`.
**How to avoid:** add a regression test asserting `FsbLatticeReplay`-style `classifyReplayEntry({tool:'mcp:set-setting', success:true, …}).availability === 'unsupported'` (same for `mcp:get-settings`). Never add either type to `READ_TOOLS` / `PER_STEP_TOOLS` / `LEGACY_WRITE_TOOLS` in `extension/utils/lattice-replay.js`.

### Pitfall 7: Stale SW discovery cache rejects valid model ids
**What goes wrong:** `modelName` writes for a model the panel discovered minutes ago are refused.
**Why it happens:** `getDiscoveredModelIds` reads the SW's in-memory `_cache`, which `_hydrateCacheFromStorage` fills once (`_hydratedFromStorage` latch). The panel's discovery runs in the panel context and only persists to `fsbDiscoveryCache` `[VERIFIED: model-discovery.js:254-347]`.
**How to avoid:** the handler reads `chrome.storage.local.get('fsbDiscoveryCache')` and applies the same rule as `getDiscoveredModelIds`: keys starting `provider + ':'`, `expiresAt > now`, `result.ok === true`, ids from `result.models`. Union that with `Config.availableModels[provider]`.

### Pitfall 8: An agent cap at its limit locks fresh sessions out of `settings`
**What goes wrong:** a new MCP session cannot read or raise `fsbAgentCap` when the cap is full.
**Why it happens:** `sendAgentScopedBridgeMessage` → `agentScope.ensure()` → `agent:register` → registry returns `AGENT_CAP_REACHED` `[VERIFIED: mcp-tool-dispatcher.js:3053-3075]`.
**How to avoid:** accept as a documented limitation (Control Panel is the fallback). Writes without an `agentId` must be refused (fail closed), so there is no unscoped bypass. See Open Question 2.

### Pitfall 9: Concurrent writes report the wrong `previous`, or interleave the provider pair
**How to avoid:** serialize `mcp:set-setting` handling with a module-level promise chain (the `_withLabelStorageLock` style already in the dispatcher). Write `modelProvider` + `modelName` in ONE `chrome.storage.local.set` call so listeners see one change event.

### Pitfall 10: No-op detection against an absent key
**What goes wrong:** writing `true` to an unset `showSidepanelProgress` returns `changed: []`, but `config.js` consumers still see `false`.
**How to avoid:** no-op only when a stored value exists and `===` the parsed value. When the key is absent, write it, which materialises one value for every consumer.

### Pitfall 11: Parallel plans fighting over `package.json`'s single-line `test` script
**What goes wrong:** two plans in one wave each append a command, giving a merge conflict on one enormous line and in `REFINEMENT_ROOT_TEST_COMMANDS`.
**How to avoid:** registration happens in the same commit as each new test (gotcha 2), so no two plans that add tests should share a wave, or one plan per wave owns registration. Config has `parallelization: true`; serialize the test-adding plans.

### Pitfall 12: `mcp-tool-smoke` is not in `npm test`
**What goes wrong:** the planner assumes `npm test` exercises the smoke edit.
**Why:** it runs only in `test:mcp-smoke` (CI job 2). `test:mcp-smoke` also runs the pre-existing failing `mcp-lifecycle-smoke`.
**How to avoid:** verify with `npm run test:mcp-smoke:tools` (build + tool smoke only).

### Pitfall 13: Phase 69 will intentionally break the 72-tool digest
**What goes wrong:** Phase 69 (executed next) shortens every description, so the D-21 baseline digest assertion goes red there.
**How to avoid:** name the constant `BASELINE_8A058BDF_TOOLS_DIGEST`. Keep it in one place, with a comment that Phase 69 replaces this assertion with its own baseline (and keeps the `8a058bdf` value for its token comparison). Pin the `settings` tool's own description and schema separately so Phase 69 can decide whether to shorten it.

## Open Questions (RESOLVED)

1. **Should the preflight (Pattern 5) be adopted?**
   - What we know: the old-extension journal leak is real (verified code path); the preflight costs one local round trip per write.
   - What's unclear: whether the owner wants MCP-side logic beyond schema plumbing (Minimal MCP diff). The logic is generic and key-free, so SC4 holds.
   - Recommendation: adopt it. It keeps every secret value inside the MCP process unless the key is known-writable on a supporting extension, and turns version skew into a clear typed error.
   - RESOLVED: adopted. The settings tool sends `mcp:get-settings {key}` first and sends the value only for a known-writable key; an unsupported reply becomes `SETTING_UNSUPPORTED` (plan 66.1-03, proven in 66.1-07).
2. **Agent cap full → fresh sessions cannot use `settings`.**
   - Recommendation: document it as a known limitation (the Control Panel is the fallback). Do not add an unscoped path. Optionally list it for V5 observation.
   - RESOLVED: known limitation, no unscoped path; accepted as T-66.1-20 and listed as a V5 observation (plan 66.1-05; VALIDATION.md Manual-Only table).
3. **Group rule for `agentProviderId = ""` while `providerKind = agent`.**
   - Recommendation: refuse with the provider-not-ready code (A3). The planner may instead accept it and document `normalizeSettings`' fallback to `api`.
   - RESOLVED: refused with `SETTING_PROVIDER_NOT_READY` while `providerKind` is `agent` (plan 66.1-02 planWrite).
4. **Should a single-key read of `modelName` include known ids?**
   - Recommendation: yes, as `values` capped at 25 (Claude's discretion). Use the same capped list in the D-15 error.
   - RESOLVED: yes. `MODEL_LIST_CAP` = 25 (plan 66.1-01); the single-key read carries `values` (plan 66.1-05); the D-15 error carries the same capped `values` (plan 66.1-02), and planWrite appends them to its value-free sentence as an `Allowed:` clause with `(+N more)` past the cap (plan 66.1-02). `errors.ts` passes the sentence through unchanged (plan 66.1-03, minimal MCP diff), asserted end to end in 66.1-07.
5. **Length bounds.**
   - Recommendation: `key` ≤ 64 (matching the D-18 pattern), `value` ≤ 2048 at the MCP handler (checked after zod, without echoing the value); per-key string bounds in the schema (`modelName` ≤ 200).
   - RESOLVED: adopted as recommended: `SETTINGS_KEY_MAX` 64 and `SETTINGS_VALUE_MAX` 2048 in the handler (plan 66.1-03); `KEY_PATTERN`, `VALUE_MAX_LENGTH` 2048 and per-entry `maxLength` (`modelName` 200, `agentProviderId` 64) in the schema (plan 66.1-01).

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Prompt-injected delegated agent changes settings (e.g. disables recording, raises caps) | Elevation / Tampering | D-20 write refusal in the extension, fail closed; the static FSB agent prompt already requires human handoff before a "settings write" |
| Endpoint redirection to exfiltrate API keys / hash key / page context | Information disclosure | D-11: `customEndpoint`, `lmstudioBaseUrl`, `serverUrl` write-protected |
| Secret readback | Information disclosure | Fixed `"[set]"` marker; never prefix/suffix/length/hash |
| Secret value persisted via journal/log/error echo | Information disclosure | Pattern 4 sanitizer + full-projection allowlist; handler never throws; no value in messages; sentinel test |
| Version skew: old extension journals the raw payload | Information disclosure | Pattern 5 preflight (value sent only for known-writable keys) |
| A client silently turning off session recording | Repudiation | D-18 `automationLogger` line regardless of recording toggle; readable via `get_logs` |
| Replay re-applying a settings write | Tampering | `classifyReplayEntry` → `unsupported` (regression test); value never persisted |
| Oversized values / write storms | DoS | Length bounds at MCP handler and schema; write lock serializes; `chrome.storage.local` has no per-minute quota (unlike `sync`) `[ASSUMED]` |
| Path/query tokens in endpoint reads | Information disclosure | Origin-only projection (`/...` suffix), `URL.origin` drops userinfo |
| Safety-adjacent toggles writable (`enableLogin`, `captchaSolverEnabled`, `fsbTelemetryOptOut`, `debugMode`) | Tampering (accepted) | Owner decision 2026-09-29 ("everything except secrets"); logged per D-18 |
