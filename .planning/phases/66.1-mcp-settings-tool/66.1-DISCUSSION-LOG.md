## External Research

**Question:** how do the main MCP hosts handle a loosely typed `value` parameter, and do any of them reject or mishandle `anyOf` or union schemas?

- **Local probe** (MCP SDK 1.29.0, zod 3.25.76, in-memory client):
  - `z.coerce.string()` emits `{"type":"string"}` and turns `true`, `50` and `null` into `"true"`, `"50"` and `"null"`.
  - `z.preprocess(v => boolean or finite number ? String(v) : v, z.string())` also emits `{"type":"string"}`, accepts booleans and numbers as strings, and rejects `null` and objects with an input-validation error. Chosen for D-04.
  - `z.union([z.string(), z.number(), z.boolean()])` emits a type array, `{"type":["string","number","boolean"]}`, not `anyOf`. Values are kept as-is, and `null` is rejected.
  - `z.any()` emits `{}` (no type), as `trigger.condition` does today.
- **Claude Code stringifies arguments when a property schema is empty (`{}`).** The fix is explicit types. Reproduced on Claude Code 2.1.212 with SDK 1.30.0, 2026-07-30. Source: https://aident.ai/blog/fix-mcp-tool-arguments-stringified-empty-schema
- **Cursor rejects valid values under `anyOf`.** It refused integers under `{"anyOf":[{"type":"integer"},{"type":"null"}]}` with "must be one of types [integer, null], got number", although the same calls worked over raw JSON-RPC. Reported 2025-11-04, closed without a fix. Source: https://forum.cursor.com/t/mcp-parameter-validation-fails-for-integer-in-anyof-integer-null-schemas/140969
- **Gemini clients cannot take type arrays.** Clients serving Gemini (Zed, Gemini CLI paths) reduce a type array to its first type. Gemini also rejects `enum` on non-string types, which fails the whole tool registration with HTTP 400. Known from search-result summaries, not full-page reads. Sources: https://git.secluded.site/zed/commit/dec1a2a3b855fe004a47596cb236beaf4ed256a5 ; https://feedback.clickup.com/feature-requests/p/clickup-mcp-tool-schema-breaks-gemini-function-calling-max-depth-enum-on-number
- **Codex CLI:** no specific report found. A plain `type: string` is within every host's supported subset, so no host-specific handling is needed.
- **Conclusion:** use `type: string` with server-side conversion of booleans and numbers. It is the one shape that is safe on every host, and it matches the repo's existing coercion pattern. Whether each live host actually sends strings or native booleans is a V5 check; both are accepted.
