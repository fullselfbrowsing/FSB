### WR-07: A settings write that fails in transport gets page-navigation advice, and its outcome is unknown

**Files modified:** `mcp/src/tools/settings.ts`, `tests/mcp-settings-tool-contract.test.js`
**Commit:** 19310d7e
**Applied fix:**
- **New local code `SETTING_UNAVAILABLE`.** It renders under `Detected: Settings` through the existing `SETTING_.+` passthrough, so `errors.ts` is unchanged.
- **Three kinds:**
  - `no_answer`: the bridge threw on a read, or before any value was sent. The hint is to check the connection.
  - `unconfirmed`: the bridge threw after the value was sent (timeout or lost link). The hint is "The change may have been applied. Call settings with only this key to check its current value before retrying."
  - `not_run`: the extension answered with a code-less failure such as `mcp_authority_not_ready`. The error says "Nothing was changed."
- **Reasons are tokens only.** A reason is shown only as a bare token (`timeout`, `disconnected`, `mcp_authority_not_ready`). Free-text extension or bridge messages are never rendered, so no value can leak.
- **Not-connected keeps its rendering.** The exact `FSB_ERROR_MESSAGES.extension_not_connected` throw now renders like the tool's own not-connected answer. Before this fix, the long sentence fell through to "Page navigation".
- **Coded failures are unchanged.** `SETTING_*` and agent-scope codes such as `AGENT_CAP_REACHED` keep their existing rendering, so the reviewer's "route any non-`SETTING_` failure" was narrowed to failures with no code.
- New contract tests (41 checks) cover:
  - write and read timeouts
  - a preflight timeout, which sends no write
  - a dropped link mid-write
  - `mcp_authority_not_ready` on a read and on a preflight
  - code-less free-text refusals
  - the not-connected path
