# Phase 66.1 Plan 06: Settings recording hygiene Summary

**Settings calls are now recorded without the value that was submitted. The request keeps only `key` (or `[invalid]`) and the agent/recording fields. Replies are recorded as summaries: a key count for read-all, `key` and `writable` for read-one, `key`, `value`, `previous` and `changed` for an accepted write, `code` and `key` for a failure. Both types use the journal's full-result projection, so the operator's D-18 journal entry keeps the write facts. A 9-case `sk-SENTINEL-ALL-9` sweep shows a refused secret or endpoint write leaves no trace in storage, recorder entries, journal events, `automationLogger` calls, route responses, or captured console/stderr text, with recording on and with it off. Replay classifies both types as `unsupported`.**

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing critical functionality] Malformed settings payloads record nothing**
- **Found during:** Task 1
- **Issue:** the interface returns any non-object payload unchanged, and an array is copied as an object. For the two settings types, a string payload such as `'sk-...'` or `['sk-...']` would then reach the recorder entry as raw content. Today's recorder drops such entries because they have no `agentId`, but the entry still carries the value.
- **Fix:** for the settings types, `null`/`undefined` pass through. A string, number or array becomes `{}`. Every other type is untouched.
- **Files modified:** `extension/ws/mcp-tool-dispatcher.js` (covered by three cases in the suite)
- **Commit:** `7340b6aa`

### Small additions within the interface (no behaviour risk)

- **Response summary edge cases.** These shapes were not specified, so I chose the narrowest ones:
  - a non-object, non-null settings reply is recorded as `{ success: false }`
  - a failure without a `key` records no key
  - `code` is recorded only when it is a non-empty string
- **Key count.** The suite asserts `keyCount === FsbSettingsSchema.keys().length` (35 now) instead of the literal 35 in the plan's behaviour text, so Phase 68's Jev key does not break it.
- **Screenshot fixture source.** The pre-edit `sanitizeMcpMessageResponseForRecording` was not exported. I captured the fixture by evaluating that function's HEAD source text on four sample replies, not by calling an export. The captured values are pinned as `SCREENSHOT_FIXTURE`.
- **Extra coverage.** Each of these goes beyond the plan's list:
  - the sweep also scans the real recorder's session/local storage shims
  - replay is also checked with the real `getToolByName` from `extension/ai/tool-definitions.js`, plus a `click` control
  - `createReplayRecord` is run over the journal's own snapshots: every step is `unsupported`, has no `value` argument, `executable` is 0, and `validateReplayClassifications` passes
- **Recorder loading.** The real recorder is required once, under a private `chrome` and logger, because it starts an initialization pass at load. The global it registers is removed again. This keeps the suite's fake storage, listeners and logger capture untouched.
