# Phase 66.1: Code Review Report

## Narrative Findings (AI reviewer)

## Summary

Scope: the `e1e6439c..HEAD` diff, excluding `.planning` and `showcase/angular/public`. That covers the new `settings` MCP tool (`mcp/src/tools/settings.ts`), the `SETTING_*` error passthrough, the two bridge message types, the declarative `FsbSettingsSchema` in `config.js`, the dispatcher read/write routes and their recording sanitizers, and the control-panel `FSBSettingsSync` (D-16). Test files were checked only for reliability. All four new suites pass on Node 20 (`settings-schema` 1452, `settings-panel-sync` 266, `mcp-settings-route` 398, `mcp-settings-tool-contract` 236). `mcp-tool-smoke` passes 268/268.

**Secret hygiene holds.** I traced every path a submitted value could take, and none of them carries it:

- MCP preflight: a value is sent only for keys the extension reports as writable, so older extensions never receive one.
- `_handleMessage` recording identity
- `_noteIconActivity`
- dispatcher metrics, the session journal (`sanitizeMcpMessageRequestForRecording`) and the response summaries
- `automationLogger` lines
- `mapFSBError`'s stderr line and the bridge `<< Response` stderr line
- zod validation errors
- replay: settings steps classify as inspect-only/unsupported

Secrets show as `[set]`/`""`, and endpoints show origin only (userinfo, path and query stripped). Prototype-key lookups (`constructor`, `__proto__`) are guarded throughout. The delegated-write gate fails closed. I found no BLOCKER.

**The defects are in the write semantics and the panel sync:**

- A provider switch to `custom` silently blanks a working model.
- An MCP switch to `lmstudio` locks every Save in an open panel.
- `providerKind=api` skips the readiness check that `agent` gets.
- The control panel can show stale values when a write lands while `loadSettings` is running.
- A keystroke in the model search box marks the whole provider group as edited, so Save reverts MCP provider writes. This is the D-16 failure mode.
- Transport failures on a write produce page-navigation advice, and the client cannot tell whether a timed-out write was applied.
- A malformed future schema entry would take down the whole service worker instead of degrading to `SETTING_UNSUPPORTED`.

## Warnings

### WR-01: A schema validation error at load aborts the entire service worker

**File:** `extension/config/config.js:929` (with `extension/background.js:8`)
**Issue:** `var api = create(PRODUCTION_ENTRIES);` runs at script evaluation, and `buildEntry` throws a `TypeError` on any malformed entry (`invalidEntry`, lines 577-645). `config.js` is the second, unguarded `importScripts` in `background.js` (line 8). A throw there aborts evaluation of `background.js`, which takes down the bridge, the autopilot and every other SW module, not just settings.

The dispatcher was written to fail closed on a missing schema (`_resolveSettingsSchema` returns null, and the routes answer `SETTING_UNSUPPORTED`). The schema's own load defeats that. Phase 68 is planned to add an entry to exactly this array (D-08, D-17). The schema test would catch a bad entry before release, but a single typo that reaches a build turns into a dead extension.
**Fix:** Degrade instead of throwing at load:
```js
var api = null;
try {
  api = create(PRODUCTION_ENTRIES);
} catch (error) {
  if (typeof console !== 'undefined') console.error('[FSB] Settings schema disabled:', error && error.message);
}
if (api) {
  global.FsbSettingsSchema = api;
  if (typeof module !== 'undefined' && module.exports) module.exports.FsbSettingsSchema = api;
}
```
Keep `create()` itself strict so that tests and fixtures still fail loudly.

### WR-02: Switching `modelProvider` to `custom` blanks a working model, and the coupled `modelName` change is not reported or logged

**File:** `extension/config/config.js:826-828`, `extension/ws/mcp-tool-dispatcher.js:3921-3929`
**Issue:** `providerRule('modelProvider', ...)` always writes `modelName: Config.DEFAULT_MODELS[value]`, which is `''` for `custom` (and for `lmstudio`). I verified this:
```
planWrite('modelProvider','custom', {..., customEndpoint:'https://x.test/v1'})
-> patch {"modelProvider":"custom","modelName":""}
```
LM Studio has a start-time resolver (`fsbResolveLmStudioModelForStart`), but `custom` has none. `validateAndCorrectModel` returns `''` for custom, and `universal-provider.js:225/247` sends `model: ''`. So the next `run_task` fails at the provider, even though the tool reported success. The control panel never stores this state: its `saveSettings` falls back to `persistedProviderSelection.modelName || 'grok-4-1-fast'`.

The overwrite is also invisible:
- The response is `{key:'modelProvider', value:'custom', previous:'xai', changed:['modelProvider','modelName']}`. It carries neither the old nor the new `modelName`.
- The D-18 operator line (`_logSettingsWrite('info', {key, previous, value, changed, ...})`) has the same gap.

The user's previous model id (for example a long custom or OpenRouter id) is lost, with no record from which to restore it. D-18 requires "previous and new value" for each accepted write.
**Fix:**
- Report and log every key in the patch, for example `values: plan.patch` and `previousValues: { modelProvider: ..., modelName: projectValue('modelName', store, ctx) }`, or at least add `modelName` and `previousModelName` to the response and the log line.
- For `custom`, keep the stored `modelName` when it is non-blank, or refuse with `SETTING_PROVIDER_NOT_READY` ("set modelName first") instead of writing `''`.

### WR-03: An MCP switch to `lmstudio` locks every Save in an open Control Panel

**File:** `extension/ui/options.js:2331` and `:2389` (sync at `:9732-9800`; the order is pinned by `tests/settings-panel-sync.test.js:745-750`)
**Issue:** The steps that lead to the lock:
1. The MCP write `modelProvider=lmstudio` stores `modelName: ''` (WR-02).
2. In an open, untouched panel, `refreshProviderGroup` applies it. It sets the provider to `lmstudio`, empties the model select (`modelSelect.innerHTML = ''`, with no option for `''`), and moves `persistedProviderSelection` to `{api, lmstudio, ''}`.
3. The user then changes an unrelated field (for example `debugMode`) and clicks Save.
4. `saveSettings` runs `validateLmStudioSettingsSelection(normalizedProviderSettings, '')` on the whole form before `filterForSave`. The guard refuses ("Load and select an LM Studio chat model before saving"), so the debugMode edit cannot be saved.

That happens even though `filterForSave` would have dropped the untouched provider keys anyway. The lock stays until LM Studio is running and the user picks a model. The test suite pins this order ("LM guard, then filterForSave"), so the behaviour is locked in.
**Fix:** Run the provider guards only when this Save will actually write the provider group. For example, compute the provider group's touched/pending state first:
```js
const providerWillBeWritten = !globalThis.FSBSettingsSync
  || globalThis.FSBSettingsSync.willWriteProviderGroup();   // true when touched or not pending
if (providerWillBeWritten) {
  if (!validateLmStudioSettingsSelection(...)) return false;
  if (!validateHostedApiSettingsSelection(...)) return false;
}
```
Update the source-order pin in `settings-panel-sync.test.js` in the same commit. Fixing WR-02 for `lmstudio` (not blanking the model) also narrows this.

### WR-04: `providerKind=api` is accepted with no readiness check, unlike `agent` and `modelProvider`

**File:** `extension/config/config.js:846-847`
**Issue:** `providerRule('providerKind', ...)` checks readiness only for `agent` (`if (value !== 'agent') return {};`). Switching to `api` succeeds even when the current `modelProvider` has no stored API key (or `custom` has no endpoint). I verified this:
```
planWrite('providerKind','api', {providerKind:'agent', agentProviderId:'claude-code', modelProvider:'openai'})
-> ok, patch {"providerKind":"api"}
```
So a user running delegated Claude Code with no API keys can have autopilot switched to a provider that cannot authenticate. The same tool refuses the equivalent `modelProvider` write with `SETTING_PROVIDER_NOT_READY`, so the rules are inconsistent.
**Fix:** Apply the `modelProvider` readiness rule to the effective provider when switching to `api`:
```js
if (key === 'providerKind') {
  if (value === 'api') {
    var p = currentText('modelProvider', stored);
    if (isHostedProvider(p) && !storedNonBlank(stored, PROVIDER_API_KEY[p])) return { failure: failure(CODES.PROVIDER_NOT_READY, key, 'Store the ' + p + ' API key in the FSB Control Panel first.') };
    if (p === 'custom' && !storedNonBlank(stored, 'customEndpoint')) return { failure: failure(CODES.PROVIDER_NOT_READY, key, 'Set a custom endpoint in the FSB Control Panel first.') };
    return {};
  }
  ...
}
```

### WR-05: Writes that land while `loadSettings` is running are overwritten in the form by the stale snapshot

**File:** `extension/ui/options.js:1826-1827`, `:1887-1903`, `:9759`
**Issue:** `loadSettings` calls `FSBSettingsSync.reset(data)` (1826), then awaits `resolveRecommendedAgentCap()` (1827), then fills every field from the earlier `data` snapshot. For provider fields it then awaits `setProviderSelection(...)` (1903), and that await includes network discovery.

An MCP write whose `onChanged` arrives during those awaits goes into `pending` and is applied to the form. Then the resumed `loadSettings` writes the stale snapshot over it, for example `debugMode`, `providerPanelState.modelProvider`, `persistedProviderSelection` and `updateApiKeyVisibility(settings.modelProvider)`.

`filterForSave` still keeps storage correct, but the panel now shows a value that is not stored, which is the visible half of D-16. Example: the panel shows debug off while it is on, and Save reports success without changing it.

`refreshProviderGroup` also cancels discovery but never bumps `providerSettingsLoadGeneration`, as `setProviderSelection` does through `cancelPendingProviderSettingsModelLoad()`. So the in-flight load is not stopped.
**Fix:**
- In `refreshProviderGroup`, call `cancelPendingProviderSettingsModelLoad()` (through a dep), the same way a user provider change does.
- At the end of `loadSettings`, re-apply the keys that changed during the load: add `FSBSettingsSync.reconcile()`, which runs `applyToForm` for every untouched `pending` key using its `lastKnown` value. Alternatively, re-read those keys from storage.

### WR-06: Typing in the model search box marks the whole provider group touched, so Save reverts MCP provider writes

**File:** `extension/ui/options.js:9369` (`modelSearch: 'modelName'`)
**Issue:** `#modelSearch` is the combobox's filter input. Every keystroke fires `input`, which maps to `modelName`, and `noteTouched` then marks all four provider keys. Typing a filter (even one closed with Escape and no selection) counts as an edit. After that:
- an MCP `modelProvider`, `modelName` or `providerKind` write is not refreshed in the form
- the next Save writes the panel's old provider and model back over it

That is the silent revert D-16 exists to prevent, triggered by a non-edit. The alias is not needed: committing a model goes through `_commit`, which dispatches `change` on `#modelName` (the select itself, options.js ~9204), and the id-based mapping already catches that.
**Fix:** Remove `modelSearch: 'modelName'` from `ELEMENT_KEY_ALIASES`, and update the alias pin in `settings-panel-sync.test.js`.

### WR-07: A settings write that fails in transport gets page-navigation advice, and its outcome is unknown

**File:** `mcp/src/tools/settings.ts:166-170` (rendered by `mcp/src/errors.ts:183`, `:440-449`)
**Issue:** The `catch` passes the bridge error straight to `mapFSBError`. I verified the built output:
```
Detected: Page navigation
Why: Request abc (mcp:set-setting) timed out after 10000ms
Next action: Refresh page state with read_page or get_dom_snapshot, then retry.
```
`mcp_authority_not_ready` (thrown by `_routeMessage` before dispatch) renders the same way. For a write this is wrong twice over:
- The settings tool has nothing to do with the page.
- A timeout does not mean the write failed. The extension may still finish `chrome.storage.local.set` after the 10 s deadline, while the client is told it timed out and to retry.
**Fix:** Map transport failures to a settings code that tells the client to verify:
```ts
} catch (err) {
  return mapFSBError({
    success: false, code: 'SETTING_UNAVAILABLE', errorCode: 'SETTING_UNAVAILABLE',
    error: 'The FSB extension did not answer the settings request in time.',
    recoveryHint: value !== undefined
      ? 'The change may have been applied. Call settings with only this key to check its current value.'
      : 'Check that the FSB extension is connected, then call settings again.',
  });
}
```
Keep `extension_not_connected` as it is. Also route any non-`SETTING_` failure from `failure(...)`, such as `mcp_authority_not_ready`, through the same wrapper.

## Info

### IN-01: Unused `queue` parameter in `registerSettingsTool`

**File:** `mcp/src/tools/settings.ts:4`, `:106-111`
**Issue:** `queue: TaskQueue` and its type import are never used. The tool deliberately bypasses the queue (D-05). The parameter exists only to match the shape of the other `register*` calls, which invites a later "fix" that routes writes through the queue.
**Fix:** Rename it to `_queue`, with a comment that the queue is bypassed on purpose (D-05), or drop it and update `runtime.ts:56`.

### IN-02: Hand-mirrored literals across three layers

**File:** `mcp/src/tools/settings.ts:19-20`, `mcp/src/errors.ts:63`, `extension/ws/mcp-tool-dispatcher.js:3715`, `:3719`, `:924`, `:3760`
**Issue:** Several strings and rules are copied by hand:
- The recovery-hint sentence exists three times: `REQUEST_INVALID_HINT`, `SETTING_NEXT_ACTION_FALLBACK` and `SETTING_RECOVERY_HINTS.default`.
- The unknown-key sentence exists twice (`config.js:382`, dispatcher `:3719`).
- The key regex exists twice (`config.js:359`, dispatcher `:924`).
- The dispatcher hard-codes `'SETTING_*'` string literals instead of `schema.CODES`.
- `_settingsCurrentProvider` re-implements the schema's private `currentText`.

Per the producer/validator-parity convention, each copy is a silent drift point.
**Fix:** In the extension, read `schema.CODES`, `schema.KEY_PATTERN` and an exported unknown-key sentence and current-provider helper from the schema. On the MCP side, keep one exported constant and share it between `settings.ts` and `errors.ts`.

### IN-03: Settings routes are kept out of replay only by fall-through

**File:** `extension/utils/lattice-replay.js:36-41` (classification at `:290-312`)
**Issue:** `mcp:get-settings` and `mcp:set-setting` are classified inspect-only only because they are in no tool set and `getToolByName` does not know them. `fsbReplayDispatchStep` (`background.js:8658-8660`) dispatches any `mcp:` step that `hasMcpMessageRoute` accepts. So a future registry alias, or a change to the classification order, would make recorded settings writes replayable. Since `value` is stripped from the journal, a replayed write would then log a refusal on every replay.
**Fix:** Add both types to `INSPECT_ONLY_TOOLS` explicitly, with a short reason ("Settings calls are not browser replay steps").

### IN-04: `noteSaved` clears `touched` in the asynchronous storage callback

**File:** `extension/ui/options.js:2403`, `:9505-9506`
**Issue:** `touched.clear()` runs when `chrome.storage.local.set` calls back, not when Save is clicked. A field the user edits between the click and the callback loses its touched mark. A later external write to that field then overwrites the unsaved edit in the form, and the next Save drops it. The window is small.
**Fix:** Before the `set` call, take a snapshot of the keys that were touched (`const savedTouched = new Set(touched)`). In the callback, clear only those keys.

### IN-05: Telemetry and session-recording toggles can be written in both directions

**File:** `extension/config/config.js:427`, `:430`
**Issue:** By the owner's explicit choice (D-09), any MCP client can set `fsbTelemetryOptOut=false`, re-enabling telemetry the user opted out of. It can also set `fsbMcpSessionRecordingEnabled=false`, which hides its later calls from the journal. The D-18 operator line still records both writes.

This is not a defect against the spec. It is noted because a prompt-injected agent could undo a privacy choice.
**Fix (owner decision):** Consider an asymmetric rule: MCP may opt out of telemetry and turn recording on, but not the reverse. Alternatively, surface these writes in the panel.
