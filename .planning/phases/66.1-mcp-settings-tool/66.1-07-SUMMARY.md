# Phase 66.1 Plan 07: Settings tool built-runtime contract and end-to-end proof Summary

**One ports-free suite now proves the `settings` tool from an MCP host's side. A real SDK Client lists and calls the built tool. The 72 tools from `8a058bdf`, the six prompts (with the 49-tool table) and the five resources (with `fsb://config`) are pinned byte-identical by digest. Reads and writes are followed through the real dispatcher into a fake `chrome.storage`. Delegated writes are refused, a protected value never leaves the MCP process, and a fixture schema key works with no `mcp/src` change.**

## Accomplishments

### Part 1: the built-runtime contract (Task 1, 172 checks)

- **Tool shape:**
  - exactly one `settings` tool, found by name
  - the plan-03 description (151 characters, at most 200)
  - the inputSchema equals the pinned JSON. Checked separately: no `required`, no `anyOf`/`oneOf`/`allOf`, no type array, no `maxLength`, both properties plain `string`.
  - no annotations
  - no tool in `tools/list` uses `anyOf` or a type array
- **Byte identity (D-21):**
  - tools minus `settings` match the tools digest
  - `listPrompts` plus every `getPrompt` reply (fixed arguments) match the prompts digest
  - the `tool-reference` text matches its own sha256 and starts with `# FSB Tool Reference (49 tools)`
  - `listResources` plus `listResourceTemplates` match the resources digest
  - reading `fsb://config` records exactly one `{ type: 'mcp:get-config', payload: {}, opts: { timeout: 10000 } }`, and the read returns the canned payload pretty-printed as `application/json`
- **Every runtime:**
  - two `createRuntime()` calls each list `settings`
  - `mcp/src/index.ts` and `mcp/src/http.ts` both call `createRuntime(`, and `runtime.ts` registers the tool exactly once
  - `TOOL_REGISTRY` has no `settings`, and `TaskQueue.readOnlyTools` lacks `'settings'`
- **Built `mapFSBError`:**
  - all 8 `SETTING_*` codes render under `Detected: Settings`, with the code verbatim in the Why line, with and without a sentence
  - a recovery hint is used verbatim; with no hint (or a blank one) the Next action is the one settings fallback, never `Update the MCP server/extension pair`, and never `Page navigation`
  - a sentence naming `modelName` is not `configuration_error`, and `not found` is not `element_not_found`
  - `{success:false, error:'Element not found'}` still renders its exact pre-66.1 text
  - an `Allowed: 50 to 500.` clause passes through once, unchanged
  - `values`/`range`/`value` fields are never rendered (no `SENTINEL`, no `Allowed:`, no `1 to 2`)
- **MCP edge (SC2):**
  - `true`, `50` and `1.5` reach `mcp:set-setting` as `'true'`, `'50'` and `'1.5'`
  - `null`, an object and an array are refused with `isError`, make no bridge call and are not echoed
  - value without key, a 65-character key (read and write) and a 2049-character value each return `SETTING_REQUEST_INVALID` with zero bridge calls and no echo; a 64-character key is allowed through
- **Preflight (Pattern 5):**
  - an `Unknown MCP message type` reply gives `SETTING_UNSUPPORTED`, and no `mcp:set-setting` is sent
  - `writable:false` and `SETTING_UNKNOWN_KEY` replies send `mcp:set-setting` with no `value` property
  - an `AGENT_CAP_REACHED` preflight sends no write
- **One line:** read-all, read-one and write outputs have no newline, parse to exactly the D-07 keys (extra extension fields are dropped), and are compact JSON.

### Part 2: end to end through the real dispatcher (Task 2, 64 more checks)

Path: MCP Client, then the built tool, then the fake bridge, then the real `dispatchMcpMessageRoute` and handlers, then a fake `chrome.storage` (callback and promise forms, set spy, `onChanged`). `delegation-providers.js`, `config.js` and the dispatcher are required after the fakes are installed. Every global is restored in `finally`.

- **Read-all** returns the schema's 35 keys, `apiKey` as `'[set]'` and 11 read-only keys, with no `sk-E2E` text.
- **Read-one** returns exactly `{"key":"maxIterations","value":100,"type":"integer","writable":true,"range":{"min":50,"max":500}}`.
- **Write `debugMode` true** returns exactly `{"key":"debugMode","value":true,"previous":false,"changed":["debugMode"]}`. There is one set call, `{debugMode:true}`, and a `Config` instance's cache is cleared by `onChanged`.
- **Refusals, with storage unchanged:**
  - `maxIterations` 600 gives `SETTING_VALUE_INVALID` with `Allowed: 50 to 500`
  - with `xai` stored, `modelName` lists `grok-4-1-fast`
  - `agentProviderId` lists `claude-code` and `grok-build`
  - `sttProvider` gives `Allowed: browser, whisper`
  - none of the three echoes its `SENTINEL-*` value
- **Protected key:** `apiKey` = `sk-NEW-SENTINEL` gives `SETTING_PROTECTED_KEY`.
  - the value is in no bridge message, storage value, `automationLogger` call, recorder entry, or captured console/stderr text
  - storage still holds `sk-E2E-SENTINEL`
  - the operator refusal line is written
- **`modelProvider` gemini** (with `geminiApiKey` stored) returns `changed ['modelProvider','modelName']` in one set call. Storage then holds `gemini` / `gemini-2.5-flash`.
- **Delegated agent** (`agent_delegated` from `agent:register`): its write gives `SETTING_DELEGATED_WRITE_REFUSED` and changes nothing. Its read succeeds, and every settings message carried the delegated `agentId`.
- **SC4 fixture:**
  - with `FsbSettingsSchema.create([...entries, fsbFixtureFastMode])`, read-all shows the fixture key as `false`, and a write returns `changed ['fsbFixtureFastMode']` and stores it
  - after the production schema is restored, the key is gone from `keys()` and reads as `SETTING_UNKNOWN_KEY`
  - `mcp/src/tools/settings.ts` contains no quoted production key
- **Whole-run sinks:** no network call. No recorder entry or logger call from Part 2 contains any `SENTINEL` text (submitted or stored). The final console/stderr scan over both parts is clean.

## Deviations from Plan

### Small choices within the plan (no behaviour change)

- **Key count:** the plan's behaviour text says read-all has 35 keys. The suite checks `keys().length === 35` and that the reply's keys equal the schema keys. When Phase 68 adds the Jev key, only that one literal needs to change.
- **Client inventory:** AgentScope's lazy `agent:register` runs the client inventory sweep, which can spawn `claude`/`codex`/`opencode --version`. The suite answers it with the existing test hook `__configureClientInventoryForTests` (fixed platforms, `ENOENT` for every probe), the precedent in `mcp-client-identity-integration`. It resets the hook at the end. No bridge member besides `isConnected` and `sendAndWait` is used.
- **Extra checks beyond the listed behaviours:**
  - a blank recovery hint
  - no `Raw error:` line
  - the 64-character key boundary
  - extra extension fields dropped from the success output
  - the `D-18` refusal line present for `apiKey`

  - the shipped agent ids asserted at setup
