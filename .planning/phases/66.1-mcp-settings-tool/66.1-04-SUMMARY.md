# Phase 66.1 Plan 04: Control Panel sync for external settings writes Summary

**An open Control Panel now follows settings written outside it (the MCP settings tool, a second panel tab): untouched fields, including the provider group, refresh in place with their persisted baselines and with no model discovery or network call, and Save leaves out every externally changed key the user did not touch, so it can no longer revert an MCP write.**

## Accomplishments

- **`FSBSettingsSync` IIFE** at the tail of `extension/ui/options.js`, after `FSBModelCombobox` and before `module.exports`. It is frozen, declares no new top-level name, and is pure at load: no listener is installed until `attach()` runs. It reads `FsbSettingsSchema` lazily; with no schema, every function is a safe no-op that drops nothing.
  - `keyForElementId`, `noteTouched` (any provider key marks all four), `noteSelfWrite`, `noteStorageChanges` (returns `{ apply }`), `filterForSave`, `noteSaved`, `reset`, `applyToForm`, `attach`, plus `inspect()`, which returns key names only, never values.
  - `applyToForm` reuses the load path's statements: value/stepper/display triplets plus `refreshStepper`, `setAgentCapControlValue`, the CAPTCHA and login visibility helpers, `sttProvider` as `value === 'whisper'`, `voiceInputEnabled` together with `persistedVoiceInputEnabled`, the element-cache preset/custom switch with a custom-select label re-sync, the trigger-cap and retention clamps, `autoAnalyzeToggle`, and the inverse telemetry toggle.
  - It never dispatches events, never marks the form dirty, never shows a toast, never logs values, and never touches secret or endpoint inputs. Secret and endpoint keys changed externally are still marked pending, so Save will not overwrite another writer.
  - **Provider refresh (no network):**
    1. Builds the shown selection from `providerPanelState` and `persistedProviderSelection.modelName`, overlays the changed keys, and normalises with `FSBProvidersPanel.normalizeSettings`.
    2. Cancels discovery (restoring the UI of any in-flight request).
    3. Updates `providerPanelState` and sets the provider select to `activeProviderId`.
    4. Rebuilds the model select with only the stored model when the provider changed; otherwise it adds the stored model only if missing and selects it.
    5. Updates the API-key group, resets the description, re-enables the model controls, and sets the info chip `Provider changed outside this panel. Refresh models to list more.`
    6. Refreshes the combobox, `renderProviderKind()` and the select labels.
    7. Sets `persistedProviderSelection` to the shown selection, so the hosted live-model-list Save gate treats it as unchanged.
- **Wiring** (three small edits plus the Save callback):
  - `setupEventListeners`: one guarded `globalThis.FSBSettingsSync.attach()` after the existing `chrome.storage.onChanged` block. The existing listener and its arms are unchanged. `attach()` installs its own onChanged listener and capture-phase `input`/`change`/`click` listeners on `document`.
  - `loadSettings`: the guarded `reset(data)` sits right after `data = data || {};`, before the first await. The LM Studio migration calls `noteSelfWrite({ modelName: migratedModel })` immediately before its `chrome.storage.local.set`.
  - `saveSettings`: `filterForSave(settings)`, then `noteSelfWrite(settings)`, immediately before `chrome.storage.local.set(settings, ...)`. In the callback, `persistedVoiceInputEnabled` and `handleSavedChange` move only when `voiceInputEnabled` was written. `persistedProviderSelection` keeps its previous field for each provider key that was dropped. `noteSaved(Object.keys(settings))` runs after filtering.
- **`tests/settings-panel-sync.test.js`** (266 checks; Node 24, `npx --offline -y node@20`, and `/tmp/fsb-node20/.../node` all pass):
  - two fresh requires install nothing until `attach()`
  - the alias map is checked against `control_panel.html`
  - touched, pending and filter behaviour, including the provider group
  - self-write records, including checker W8 and the double-Save case
  - `noteSaved` and `reset`
  - every simple refresher, the element cache, removal, secrets and endpoints
  - the provider refresh with injected deps: the gemini switch, a same-provider model, an agent switch, the retired-agent reselection, and an unknown id
  - no-schema safety
  - source contracts for `saveSettings`, `loadSettings`, `discardChanges` and `setupEventListeners`, and the forbidden-token scan of the IIFE
  - the live `attach()` listeners with the real default deps: maxIterations and provider refreshes, touched suppression, the Reset click, and no `fetch`, `runDiscovery` or dispatched events

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Discovery is cancelled with `restoreUi: true`**
- **Found during:** Task 1
- **Issue:** The plan says `invalidateProviderDiscovery(false)`. When a list request is in flight (the initial load, or a key-change debounce), cancelling without restore leaves the model select and Refresh button disabled in their loading state, and nothing re-enables them.
- **Fix:** The default `invalidateDiscovery` dep calls `invalidateProviderDiscovery(true)`. This restores the pre-request snapshot (DOM only) before the model select is rebuilt. It still starts no request.
- **Files modified:** `extension/ui/options.js`
- **Commit:** `aefcd882`

**2. [Rule 2 - Missing functionality] The model controls are re-enabled when the provider changed**
- **Found during:** Task 1
- **Issue:** The old provider's state could leave the controls disabled, for example when its API key was missing. The new info chip tells the user to press Refresh models, which would then be disabled.
- **Fix:** A `setControlsDisabled(false)` dep (`FSBDiscoveryUI.setControlsDisabled`, DOM only) runs only when the provider changed. It is counted in the dep tests.
- **Files modified:** `extension/ui/options.js`, `tests/settings-panel-sync.test.js`
- **Commit:** `aefcd882`

**3. [Rule 2 - Missing functionality] Reset-button edits count as touched**
- **Found during:** Task 1
- **Issue:** The plan installs only `input` and `change` listeners. The agent-cap and trigger-cap Reset buttons change the value on `click` with neither event. An external write would then be applied over the user's pending reset, against D-16 ("their pending edit wins on Save").
- **Fix:** One more capture-phase `click` listener that acts only when `closest('#fsbAgentCapReset, #fsbTriggerCapReset')` matches. A plain click on a field does not mark it touched; a test pins this.
- **Files modified:** `extension/ui/options.js`, `tests/settings-panel-sync.test.js`
- **Commit:** `aefcd882`

**4. [Rule 1 - Bug] The telemetry toggle refreshes as an inverse toggle**
- **Found during:** Task 1
- **Issue:** `fsbTelemetryOptOut` is a writable key, but its checkbox means telemetry ON. A plain `checked = value` refresh would show the opposite of the stored state.
- **Fix:** `checked = value !== true`, plus the `aria-label` strings `install-identity-ui.js` sets. The suite checks both strings against that file.
- **Files modified:** `extension/ui/options.js`, `tests/settings-panel-sync.test.js`
- **Commit:** `aefcd882`

**5. [Rule 1 - Bug] Self-write records compare against the last pending self-write first**
- **Found during:** Task 1
- **Issue:** Two quick Saves of the same new value: both compare against the unchanged `lastKnown`, so both record, but only one echo arrives. The stale record could later swallow a real external change. This is the same class as checker W8.
- **Fix:** The comparison baseline is the last pending self-write for the key, else `lastKnown`. Each key's queue is bounded at 8. A test covers the double-Save case.
- **Files modified:** `extension/ui/options.js`, `tests/settings-panel-sync.test.js`
- **Commit:** `aefcd882`

**6. [Rule 1 - Bug] Wrong assumption in my own Task 2 RED check**
- **Found during:** Task 2
- **Issue:** I first asserted that `setupEventListeners` registers exactly one onChanged listener. It already registers two: the counter block, and the analytics/memory listener at ~1320.
- **Fix:** The check now pins the existing two. The sync's own listener comes through `attach()`.
- **Files modified:** `tests/settings-panel-sync.test.js`
- **Commit:** `72f0e4ea`

## Known limitations (not stubs)

- **Load window:** an external write that lands while `loadSettings` is still awaiting its first provider discovery (about the first second after the panel opens) is tracked, and Save still protects it. The load path may then paint its older snapshot over the refreshed field. This is display only, until the next reload.
- **Immediate-write toggles:** `autoAnalyzeToggle` and the telemetry toggle stay touched after a user flip until the next Save or load. A later external write to that same key shows only after a reload. There is no revert risk, because `saveSettings` never writes those keys.
- **The panel's own writes outside saveSettings:** the autoAnalyze and telemetry toggles and the Sync tab's `serverUrl`/`serverHashKey` are not recorded as self-writes, so they are marked pending. This has no effect, because `saveSettings` never writes those keys.
- **Unchanged post-Save statement:** `if (settings.providerKind === 'api' && settings.apiKey) checkApiConnection();` is kept exactly as the plan requires. After a Save that dropped an externally changed `providerKind`, that post-Save connection check does not run. The user can still press Test Connection.
